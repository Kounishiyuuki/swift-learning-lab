# Concurrency & Memory

このファイルは人が読みやすい教材原本です。構造化データは content.json、完成版は index.html です.

## 01. Error Handling・throws / do-catch / defer [Basic]

概要: 失敗する処理を型と制御フローで明示的に扱う。
考え方: Errorは『想定外でcrash』ではなく『この操作は失敗し得る』ことをAPIに表す。

重要ポイント:
- Error準拠型で失敗理由。
- throws関数をtryで呼ぶ。
- do-catchで回復。
- deferでscope終了時の後処理。

コード:
```swift
enum LoadError:Error{case invalid}
func load() throws -> String { throw LoadError.invalid }
do { _=try load() } catch { print(error) }
```

なぜ重要か: network、file、decode、永続化など失敗するI/Oで必須。
注意: try?で何でもnil化するとerror理由が消える。

確認問題:
Q1. throws関数の通常呼び出しに必要なのは？ [Basic]
```swift
func load() throws -> String{"OK"}
let x=/* ? */ load()
```
A. try
B. await
C. weak
D. mutating
正解: A
解説: throws関数はtryで呼ぶ。

詳しい解説:
- 用語・考え方: `throws` は「この関数は失敗してエラーを投げることがある」という宣言です。呼ぶ側はその可能性を無視できず、`try` を書いて「失敗しうる呼び出しである」ことを明示します。実際にエラーを受け止めるには do-catch で囲むか、自分も throws を付けて呼び出し元へ伝播させます。
- 正解になる理由: try は「ここで失敗するかもしれない」という目印です。コードを読むだけで失敗しうる箇所が分かるため、エラー処理の漏れに気づきやすくなります。
- 他の選択肢 await: await は非同期関数の呼び出しに使う記号で、処理が一時中断されうる地点を示します。エラーとは別の話で、両方必要なら `try await` と書きます。
- 他の選択肢 weak: weak は参照カウントを増やさない参照の指定で、メモリ管理のためのものです。
- 他の選択肢 mutating: mutating は struct のメソッドが自身を書き換えることを示す指定です。
- 覚えておくこと: throws には try、async には await。両方なら `try await`。

Q2. deferはいつ実行？ [Basic]
```swift
func f(){defer{print("end")};print("body")}
```
A. scopeを抜ける直前
B. 最初
C. compile時
D. 実行されない
正解: A
解説: scope終了時に実行。

詳しい解説:
- 用語・考え方: defer は「このスコープを抜ける直前に必ず実行する処理」を登録する仕組みです。正常に最後まで進んだ場合も、途中で return した場合も、エラーを投げて抜けた場合も実行されます。ファイルを閉じる、フラグを戻すといった後始末をまとめて書けます。
- コードの流れ: 関数に入り、defer ブロックが「後で実行する処理」として登録される（この時点では実行されない）。
- コードの流れ: print("body") が実行される。
- コードの流れ: 関数を抜ける直前に、登録された defer の中身が実行され end が出力される。
- 正解になる理由: 登録の順ではなく、スコープを抜けるタイミングで実行される点が defer の要点です。書く場所と実行される場所がずれます。
- 他の選択肢 最初: 登録は最初に行われますが、実行は最後です。この順序の違いが defer の特徴です。
- 他の選択肢 compile時: 実行時の仕組みであり、ビルド時に何かが起きるわけではありません。
- 他の選択肢 実行されない: スコープを抜ければ必ず実行されます。途中で return しても実行されます。
- 関連例:
```swift
func run() {
    defer { print("end") }
    print("body")
}
run()
```
- 関連例の出力: body
end
- 関連例の説明: defer は先に書かれていても、実行されるのはスコープを抜ける直前です。後始末を処理の近くに書けるのが利点です。
- 覚えておくこと: defer は「抜ける直前に必ず実行」。

## 02. Result<Success, Failure> [Basic]

概要: 成功/失敗を値として持ち運ぶResult型を理解する。
考え方: throwsが制御フローなら、Resultは成功/失敗をdataとして保持する。

重要ポイント:
- .success(value) / .failure(error)。
- completion APIで頻出。
- get()で成功値取得またはthrow。
- async throwsへ移行できる場合も多い。

コード:
```swift
func load(completion:(Result<Data,Error>)->Void){ }
```

なぜ重要か: legacy callback APIやlibraryで頻出。
注意: throwsとResultは用途が違う。失敗を値として保持したいかで考える。

確認問題:
Q1. Resultの主要caseは？ [Basic]
```swift
Result<Int,Error>
```
A. success/failure
B. some/none
C. on/off
D. left/right
正解: A
解説: 成功と失敗をenum caseで表す。

詳しい解説:
- 用語・考え方: Result は「成功したときの値」と「失敗したときのエラー」を 1 つの値として表す enum です。`.success(値)` と `.failure(エラー)` の 2 つの case を持ち、結果をその場で処理せずに保持したり、あとから受け渡したりできます。
- 正解になる理由: 成功と失敗を型で表すため、呼び出し側は switch で両方の場合を扱うことを強制されます。処理し忘れが起きにくくなります。
- 他の選択肢 some/none: Optional の内部表現の case 名です。値の有無を表すもので、失敗の理由は持てません。
- 他の選択肢 on/off: Result の case 名ではありません。
- 他の選択肢 left/right: Either 型を持つ他の言語での命名です。Swift の Result は success / failure です。
- 覚えておくこと: Result は成功値と失敗理由を 1 つの値にまとめる。

Q2. result.get() がfailure時どうなる？ [Intermediate]
```swift
try result.get()
```
A. Errorをthrow
B. nil固定
C. 0
D. compile error
正解: A
解説: 保持Errorをthrowする。

詳しい解説:
- 用語・考え方: `get()` は Result から成功値を取り出すメソッドです。`.success` なら中の値を返し、`.failure` なら保持しているエラーを throw します。そのため呼び出しには try が必要で、do-catch と組み合わせて使います。
- コードの流れ: result が .success(値) なら、get() はその値をそのまま返す。
- コードの流れ: result が .failure(エラー) なら、get() はそのエラーを throw する。
- コードの流れ: 呼び出し側は try で受け、catch でエラーを処理する。
- 正解になる理由: Result を throws の世界へ橋渡しするのが get() の役割です。switch で分岐する代わりに、do-catch で扱えるようになります。
- 他の選択肢 nil固定: nil を返す API ではありません。nil で表すなら Optional を使います。Result は失敗の理由まで保持します。
- 他の選択肢 0: 既定値で埋めることはありません。既定値が欲しい場合は自分で `?? 0` 相当の処理を書きます。
- 他の選択肢 compile error: try を付ければ正しくコンパイルできます。
- 関連例:
```swift
enum LoadError: Error { case notFound }
let ok: Result<Int, Error> = .success(3)
let ng: Result<Int, Error> = .failure(LoadError.notFound)
do {
    print(try ok.get())
    print(try ng.get())
} catch {
    print("caught \(error)")
}
```
- 関連例の出力: 3
caught notFound
- 関連例の説明: 成功なら値が返り、失敗なら保持していたエラーが投げられて catch に入ります。1 つ目の print は実行され、2 つ目は中断されます。
- 覚えておくこと: get() は成功なら値、失敗なら throw。

## 03. ARC・Object Lifetime [Intermediate]

概要: class instanceの寿命をreference countで管理する仕組みを理解する。
考え方: ARCは『誰かが強く必要としている間だけclassを生かす』仕組み。

重要ポイント:
- strong reference中は保持。
- referenceがなくなるとdeinit。
- structの値semanticsとは別。
- 循環参照は自動解消できない。

コード:
```swift
final class User{deinit{print("deinit")}}
var user:User?=User()
user=nil
```

なぜ重要か: UIKit、delegate、closure、service lifetime理解に必須。
注意: ARCはGCのように循環を自動検出して回収しない。

確認問題:
Q1. class instanceが通常解放される条件は？ [Intermediate]
```swift
var obj:MyClass?=MyClass()
obj=nil
```
A. strong referenceがなくなる
B. 1秒経つ
C. GCが必ず検出
D. let使用
正解: A
解説: ARCはstrong reference countに基づく。

詳しい解説:
- 用語・考え方: Swift は ARC（Automatic Reference Counting）でクラスのインスタンスを管理します。そのインスタンスを強く参照している変数の数が数えられていて、0 になった時点で解放されます。定期的に走査して回収する方式ではなく、参照が切れたその場で解放される点が特徴です。
- コードの流れ: MyClass() が作られ、obj が強く参照するので参照数は 1。
- コードの流れ: `obj = nil` で obj からの参照が外れ、参照数が 0 になる。
- コードの流れ: 参照数が 0 になった時点で解放され、deinit があれば呼ばれる。
- 正解になる理由: 解放の条件は「強い参照が 1 つも残っていないこと」です。weak や unowned の参照は数に含まれないため、それだけが残っていても解放されます。
- 他の選択肢 1秒経つ: 時間経過では解放されません。参照が残っていれば残り続けます。
- 他の選択肢 GCが必ず検出: Swift は走査型のガベージコレクタを使いません。参照数が 0 になった時点で決まったタイミングで解放されます。
- 他の選択肢 let使用: let か var かは、その変数を後から差し替えられるかどうかの違いであり、解放の条件ではありません。
- 関連例:
```swift
final class Session {
    deinit { print("released") }
}
var session: Session? = Session()
print("before")
session = nil
print("after")
```
- 関連例の出力: before
released
after
- 関連例の説明: nil を代入した瞬間に参照数が 0 になり、その場で deinit が呼ばれます。解放のタイミングが確定している点が ARC の特徴です。
- 覚えておくこと: 強い参照が 0 になった瞬間に解放される。

Q2. ARCが自動解決できない代表問題は？ [Intermediate]
```swift
a.b=b; b.a=a
```
A. strong reference cycle
B. Int加算
C. Array sort
D. URL encoding
正解: A
解説: 相互strong参照で解放されない。

詳しい解説:
- 用語・考え方: 2 つのインスタンスが互いを強く参照し合うと、どちらの参照数も 0 になりません。外部からの参照をすべて外しても両方が生き残り、メモリが解放されないままになります。これが強参照循環（strong reference cycle）です。
- コードの流れ: a が b を強く参照する。
- コードの流れ: b も a を強く参照する。
- コードの流れ: 外部の変数を nil にしても、互いの参照が残るため参照数は 0 にならない。
- コードの流れ: どちらも解放されず、メモリ上に残り続ける。
- 正解になる理由: ARC は参照数だけを見るため、この輪を自動では検出できません。設計者が weak や unowned でどちらか一方の参照を弱めて断ち切る必要があります。
- 他の選択肢 Int加算: 数値の計算はメモリ管理と関係ありません。
- 他の選択肢 Array sort: 並べ替えは値の操作であり、参照の循環とは無関係です。
- 他の選択肢 URL encoding: 文字列の変換処理であり、メモリ管理の問題ではありません。
- 覚えておくこと: 互いに強参照すると解放されない。片方を weak にして断つ。

## 04. weak・unowned・Closure Capture [Intermediate]

概要: 参照循環を避ける非所有参照とcapture listを理解する。
考え方: 所有関係を『強く持つ』『存在する間だけ弱く見る』に分ける。

重要ポイント:
- weakは通常Optionalで対象解放時nil。
- unownedは対象生存を前提。
- delegateをweakにする設計が多い。
- capture listでself保持方法を指定。

コード:
```swift
final class Child{weak var parent:Parent?}
```

なぜ重要か: delegate、completion、Coordinatorなどでmemory leakを防ぐ。
注意: weak/unownedはlifetime保証で使い分ける。

確認問題:
Q1. weak対象が解放されると？ [Intermediate]
```swift
weak var owner:Owner?
```
A. nilになる
B. 必ずcrash
C. strongへ変化
D. copy
正解: A
解説: zeroing weak referenceでnilになる。

詳しい解説:
- 用語・考え方: weak 参照は対象の参照数を増やしません。そのため対象が解放されうるので、weak な変数は必ず Optional になります。対象が解放されると、その変数は自動的に nil になります（zeroing weak reference）。解放済みの領域を指したままにならないため安全です。
- 正解になる理由: 自動的に nil になるので、使う前に if let などで確認すれば、すでに無くなった対象へアクセスする事故を防げます。
- 他の選択肢 必ずcrash: 解放済みの領域を指したままにならないため、停止しません。unowned の場合は逆に、解放後にアクセスすると停止します。
- 他の選択肢 strongへ変化: 弱い参照が自動的に強い参照へ変わることはありません。
- 他の選択肢 copy: 参照であって複製ではありません。対象がコピーされることはありません。
- 関連例:
```swift
final class Owner {
    deinit { print("released") }
}
var owner: Owner? = Owner()
weak var weakOwner = owner
print(weakOwner == nil)
owner = nil
print(weakOwner == nil)
```
- 関連例の出力: false
released
true
- 関連例の説明: 強い参照が外れた時点で対象が解放され、weak 側は自動的に nil になります。だから weak は必ず Optional として宣言します。
- 覚えておくこと: weak は Optional。対象が消えると自動で nil。

Q2. unownedの前提は？ [Intermediate]
```swift
unowned let owner:Owner
```
A. 参照中は対象が生存保証
B. いつでもnil
C. 値型だけ
D. MainActor必須
正解: A
解説: 対象lifetimeがより長いと保証できる場合。

詳しい解説:
- 用語・考え方: unowned も参照数を増やしませんが、weak と違って Optional にはならず、自動的に nil にもなりません。「自分が生きている間、相手は必ず生きている」と保証できる場合にだけ使います。保証が崩れて解放済みの対象にアクセスすると、その時点でプログラムが停止します。
- 正解になる理由: unowned は「相手のほうが自分より長生きする」という前提に依存します。子が親を参照するような、寿命の関係がはっきりしている場合に使います。
- 他の選択肢 いつでもnil: nil になり得るのは weak です。unowned は Optional ではないため nil を代入できません。
- 他の選択肢 値型だけ: 参照の話なので対象は参照型です。値型には参照カウントがありません。
- 他の選択肢 MainActor必須: 並行処理の指定とは無関係です。
- 覚えておくこと: unowned は「相手が必ず生きている」前提。崩れると停止する。

## 05. async / await [Basic]

概要: 非同期処理を直線的なcodeとして書く基本を理解する。
考え方: awaitは『Taskが一時中断され後で再開する可能性』を示す。

重要ポイント:
- async関数は非同期完了。
- awaitはsuspension point。
- async throwsならtry await。
- async=必ず別threadではない。

コード:
```swift
func load() async throws -> User{
 try await api.fetchUser()
}
```

なぜ重要か: URLSessionなどmodern Swift開発の中心。
注意: await前後で同じthreadとは限らない。

確認問題:
Q1. awaitが示すものは？ [Basic]
```swift
let user=try await load()
```
A. Taskが中断され得る地点
B. 必ずnew thread
C. Error無視
D. 同期化
正解: A
解説: suspension point。

詳しい解説:
- 用語・考え方: await は「ここで待つかもしれない」ことを示す目印です。その地点で今の処理はいったん中断され（suspension point）、実行していたスレッドは解放されて他の作業に使われます。結果が用意できたら処理が再開されます。新しいスレッドが作られるわけではありません。
- コードの流れ: await の地点まで通常どおり実行される。
- コードの流れ: 結果がまだ無ければ、この処理は中断され、スレッドは他の作業へ回される。
- コードの流れ: 結果が用意できると、続きから再開される。
- コードの流れ: 再開後のスレッドは、中断前と同じとは限らない。
- 正解になる理由: await は中断されうる地点の宣言です。中断中もスレッドが塞がらないため、少ないスレッドで多くの処理を並行に進められます。
- 他の選択肢 必ずnew thread: スレッドを新しく作る指示ではありません。むしろ待っている間はスレッドを手放します。
- 他の選択肢 Error無視: エラーとは無関係です。エラーを扱うのは try です。
- 他の選択肢 同期化: 同期処理に変えるものではありません。非同期であることを明示する記号です。
- 覚えておくこと: await は中断されうる地点。スレッド生成ではない。

Q2. async throwsの呼び出しは？ [Basic]
```swift
func load() async throws -> Data
```
A. try await load()
B. await?だけ
C. weak load()
D. load!()
正解: A
解説: throwとasyncの両方を扱う。

詳しい解説:
- 用語・考え方: `async throws` は「非同期であり、かつ失敗しうる」関数です。呼ぶ側は両方の性質を明示する必要があり、`try await` と 2 つ並べて書きます。順序は try が先、await が後です。
- 正解になる理由: await が中断されうる地点、try が失敗しうる呼び出しを示します。両方の性質があるため、両方を書きます。
- 他の選択肢 await?だけ: エラーを扱う指定が抜けています。throws である以上 try が必要です。また `await?` という記法はありません。
- 他の選択肢 weak load(): weak はメモリ管理の指定で、関数呼び出しには使いません。
- 他の選択肢 load!(): `!` は Optional の強制アンラップなどに使う記号で、非同期やエラーの扱いとは無関係です。
- 覚えておくこと: `async throws` の呼び出しは `try await`。

## 06. async let・Structured Concurrency [Intermediate]

概要: 独立した複数処理を並行に進め、親子Task構造を保つ。
考え方: 独立して待てる処理は同時開始し最後にまとめてawaitできる。

重要ポイント:
- async letでchild task開始。
- 親scopeとchild lifetimeが結び付く。
- latencyを重ねられる。
- 依存処理を無理に並行化しない。

コード:
```swift
async let user=api.fetchUser()
async let posts=api.fetchPosts()
let result=try await (user,posts)
```

なぜ重要か: 複数APIや画像loadで待ち時間を短縮できる。
注意: 同じmutable stateを複数childから変更しない。

確認問題:
Q1. async letが向くのは？ [Intermediate]
```swift
async let a=loadA()
async let b=loadB()
```
A. 互いに独立した非同期処理
B. 順番依存処理
C. 同期定数だけ
D. Auto Layout
正解: A
解説: 独立処理を並行開始できる。

詳しい解説:
- 用語・考え方: `async let` は非同期処理を「開始だけしておき、結果は後で受け取る」書き方です。2 つ書けば両方が同時に走り始めます。ただし互いの結果に依存する処理には使えません。前の結果を次に使う場合は、素直に `await` で順番に待ちます。
- コードの流れ: `async let a = loadA()` で loadA が走り始める（ここでは待たない）。
- コードの流れ: 続けて `async let b = loadB()` も走り始める。
- コードの流れ: 後で `await a` や `await b` と書いた時点で結果を受け取る。
- コードの流れ: 2 つが独立しているため、合計時間は「両方の合計」ではなく「遅いほう」に近づく。
- 正解になる理由: 独立した処理を同時に進めることが目的なので、依存関係の無い処理に向いています。
- 他の選択肢 順番依存処理: 前の結果を次で使う処理は同時に始められません。順番に await します。
- 他の選択肢 同期定数だけ: 同期的な定数の計算に非同期の仕組みは不要です。
- 他の選択肢 Auto Layout: 画面のレイアウトとは無関係です。
- 関連例:
```swift
func load(_ name: String) async -> String { name }

async let first = load("A")
async let second = load("B")
let results = await [first, second]
print(results)
```
- 関連例の出力: ["A", "B"]
- 関連例の説明: 2 つの処理は同時に開始され、await した時点で結果を受け取ります。受け取る順番はこちらが決めるため、結果の並びは安定します。
- 覚えておくこと: async let は独立した処理を同時に開始する。

Q2. Structured Concurrencyの利点は？ [Intermediate]
```swift
withTaskGroup{...}
```
A. Task lifetimeが親子構造で管理
B. Taskが永久に残る
C. ARC不要
D. HTTP不要
正解: A
解説: child taskがscopeに構造化される。

詳しい解説:
- 用語・考え方: Structured Concurrency は、非同期処理を親子関係のある構造として管理する考え方です。親のスコープを抜けるときには、その中で始めた子の処理がすべて完了（またはキャンセル）していることが保証されます。処理が迷子になって残り続けることを防げます。
- 正解になる理由: スコープと寿命が対応するため、「どこで始まり、どこで終わるか」がコードの形から読み取れます。エラーやキャンセルも親子をたどって伝わります。
- 他の選択肢 Taskが永久に残る: むしろ逆で、スコープを抜けるときに残らないことが保証されます。構造の外で独立して走らせたい場合は非構造の Task を使います。
- 他の選択肢 ARC不要: メモリ管理の仕組みは引き続き必要です。
- 他の選択肢 HTTP不要: 通信の有無とは無関係です。
- 覚えておくこと: 子タスクの寿命が親のスコープに収まる。

## 07. Task・Priority・Cancellation [Intermediate]

概要: Taskを開始し、キャンセル可能な処理として扱う。
考え方: Cancellationは強制停止ではなく『もう結果が不要』という協調的signal。

重要ポイント:
- Task{}で新task。
- Task.isCancelled / checkCancellation()。
- 一部async APIはcancelをthrow。
- 画面消失時など不要処理をcancel。

コード:
```swift
let task=Task{
 try Task.checkCancellation()
 return try await load()
}
task.cancel()
```

なぜ重要か: 検索、画像load、画面遷移で古いrequestを捨てる時に重要。
注意: cancel()で任意codeが即停止するわけではない。

確認問題:
Q1. Task cancellationの性質は？ [Intermediate]
```swift
task.cancel()
```
A. 協調的signal
B. 任意命令を即強制終了
C. app終了
D. thread kill保証
正解: A
解説: 処理側が確認/反応する。

詳しい解説:
- 用語・考え方: `task.cancel()` は「もうこの処理は不要になった」という合図を立てるだけで、実行中の処理を強制的に止めるものではありません。処理側が `Task.isCancelled` を確認したり `try Task.checkCancellation()` を呼んだりして、自分から中断する必要があります。これを協調的キャンセルと呼びます。
- コードの流れ: cancel() が呼ばれ、そのタスクにキャンセル済みの印が付く。
- コードの流れ: 実行中の処理はそのまま動き続ける。
- コードの流れ: 処理側が確認する地点に来たときに初めて中断される。
- コードの流れ: 確認する箇所が無ければ、最後まで実行されてしまう。
- 正解になる理由: 強制停止だと、途中の状態が壊れたまま放置される危険があります。処理側が安全な地点で自ら止まる設計になっています。
- 他の選択肢 任意命令を即強制終了: 任意の地点で強制的に打ち切ることはできません。確認する箇所が無ければ止まりません。
- 他の選択肢 app終了: アプリ全体が終了することはありません。対象のタスクだけの話です。
- 他の選択肢 thread kill保証: スレッドを強制終了する保証はありません。そもそもタスクとスレッドは 1 対 1 ではありません。
- 覚えておくこと: cancel は「お願い」。処理側が確認しないと止まらない。

Q2. cancelをthrowとして確認するAPIは？ [Intermediate]
```swift
try Task.checkCancellation()
```
A. CancellationErrorをthrow可能
B. Boolだけ
C. UIを閉じる
D. Git reset
正解: A
解説: cancel済みならErrorをthrowする。

詳しい解説:
- 用語・考え方: `try Task.checkCancellation()` は、キャンセル済みなら CancellationError を throw し、そうでなければ何もせずに次へ進むメソッドです。長い処理の途中に挟むことで、キャンセルへの反応点を作れます。
- 正解になる理由: throw によって以降の処理が飛ばされ、呼び出し元まで一気に抜けられます。エラー処理の仕組みにそのまま乗るため、後始末も do-catch や defer で書けます。
- 他の選択肢 Boolだけ: 真偽値だけを見たい場合は `Task.isCancelled` を使います。checkCancellation は throw する点が異なります。
- 他の選択肢 UIを閉じる: 画面操作とは無関係です。
- 他の選択肢 Git reset: バージョン管理の操作とは無関係です。
- 覚えておくこと: isCancelled は判定、checkCancellation は throw。

## 08. TaskGroup [Intermediate]

概要: 動的な数のchild taskを並行実行し、結果を集約する。
考え方: async letが固定個数ならTaskGroupは実行時に増減する仕事の集合。

重要ポイント:
- withTaskGroup / withThrowingTaskGroup。
- group.addTaskで追加。
- 結果は完了順に取得され得る。
- 親scopeでchild終了を管理。

コード:
```swift
let values=await withTaskGroup(of:Int.self){group in
 for n in 1...3{group.addTask{n*2}}
 return await group.reduce(into:[]){$0.append($1)}
}
```

なぜ重要か: 複数画像や複数endpointなど動的並行処理に使う。
注意: 入力順と完了順は一致しないことがある。

確認問題:
Q1. TaskGroup結果順について正しいのは？ [Intermediate]
```swift
for await value in group { }
```
A. 完了順になり得る
B. 必ず追加順
C. 必ず逆順
D. 取得不可
正解: A
解説: taskは並行実行される。

詳しい解説:
- 用語・考え方: TaskGroup に追加した子タスクは同時に走るため、終わる順番は処理内容や実行環境によって変わります。`for await value in group` で受け取れるのは、追加した順ではなく完了した順です。
- 正解になる理由: 並行に走る以上、どれが先に終わるかは保証できません。順序が重要なら、結果に索引や識別子を持たせて後から並べ替えるか、Dictionary に集めます。
- 他の選択肢 必ず追加順: 追加順は保証されません。速く終わったものから届きます。
- 他の選択肢 必ず逆順: 逆順になる保証もありません。順序は不定です。
- 他の選択肢 取得不可: 結果は受け取れます。順序が保証されないだけです。
- 覚えておくこと: TaskGroup の結果は完了順。順序が要るなら自分で並べ替える。

Q2. TaskGroupが向くのは？ [Intermediate]
```swift
for url in urls{group.addTask{...}}
```
A. 動的個数の並行task
B. 1個の同期計算だけ
C. Auto Layout
D. ARC解放
正解: A
解説: runtimeで数が決まる並行処理。

詳しい解説:
- 用語・考え方: `async let` は書いた数だけ処理を開始する固定的な書き方です。対して TaskGroup は、実行時に決まる個数の処理をループで追加できます。URL の配列を受け取って全件取得する、といった場面に向いています。
- 正解になる理由: 個数が実行時にしか分からない場合、`async let` では書き表せません。TaskGroup なら addTask をループで呼べます。
- 他の選択肢 1個の同期計算だけ: 1 つの同期的な計算に並行処理の仕組みは不要です。そのまま書くほうが単純です。
- 他の選択肢 Auto Layout: 画面のレイアウトとは無関係です。
- 他の選択肢 ARC解放: メモリの解放処理とは無関係です。
- 覚えておくこと: 個数が固定なら async let、可変なら TaskGroup。

## 09. Actor・Isolation [Intermediate]

概要: 共有mutable stateをactor isolationで保護する。
考え方: actorは『この状態を触る入口を1列にする』イメージ。

重要ポイント:
- actorは参照型だがstate accessが制御される。
- 外部からawaitが必要な場合。
- data raceを防ぐ。
- await中のreentrancyに注意。

コード:
```swift
actor Counter{
 private var value=0
 func increment(){value+=1}
 func current()->Int{value}
}
```

なぜ重要か: cache、共有service、並行更新で重要。
注意: actor内の処理全体がtransactionになるわけではない。

確認問題:
Q1. actorの主目的は？ [Intermediate]
```swift
actor Store{var items:[Item]=[]}
```
A. 共有mutable stateをisolationで保護
B. UI描画
C. JSON encode
D. class継承
正解: A
解説: 並行accessから内部stateを隔離する。

詳しい解説:
- 用語・考え方: 複数の処理が同時に同じ可変データを読み書きすると、結果が壊れることがあります（データ競合）。actor は自分が持つ状態への出入り口を 1 つに絞り、同時に 1 つの処理しか中へ入れないようにします。この仕組みを isolation（隔離）と呼びます。
- 正解になる理由: ロックを自分で書く代わりに、型の性質として安全性を確保できます。内部の状態は外から直接触れず、必ず actor のメソッド経由になります。
- 他の選択肢 UI描画: 画面描画そのものを担う型ではありません。UI に関わるのは MainActor という特定の actor です。
- 他の選択肢 JSON encode: データ変換は Codable の役割です。
- 他の選択肢 class継承: actor は継承のための仕組みではありません。
- 関連例:
```swift
actor Counter {
    private var value = 0
    func increment() { value += 1 }
    func current() -> Int { value }
}

let counter = Counter()
await counter.increment()
await counter.increment()
print(await counter.current())
```
- 関連例の出力: 2
- 関連例の説明: value は actor の外から直接触れません。increment も current も actor の中で 1 つずつ実行されるため、同時に呼ばれても値が壊れません。
- 覚えておくこと: actor は可変状態への同時アクセスを 1 つに絞る。

Q2. actor外からisolated methodを呼ぶ時一般に必要なのは？ [Intermediate]
```swift
let v=/* ? */ counter.current()
```
A. await
B. weak
C. override
D. mutating
正解: A
解説: actor境界を越えるためawaitが必要な場合が多い。

詳しい解説:
- 用語・考え方: actor の外からそのメソッドを呼ぶときは、actor の中に入る順番を待つ可能性があります。待ちが発生しうる以上、呼び出しは中断されうる地点になるため await が必要です。actor の内部から自分のメソッドを呼ぶ場合は、すでに中にいるので await は不要です。
- 正解になる理由: 境界を越える呼び出しは待つ可能性があるからです。await が付くことで、読み手にも「ここで他の処理に譲る可能性がある」と伝わります。
- 他の選択肢 weak: weak はメモリ管理の指定で、呼び出しには使いません。
- 他の選択肢 override: override は継承したメソッドの上書きです。
- 他の選択肢 mutating: mutating は struct のメソッドが自身を変更する指定です。actor には使いません。
- 覚えておくこと: actor の外からの呼び出しには await。

## 10. MainActor・UI Isolation [Intermediate]

概要: UI関連stateをMainActorへ隔離する考え方を理解する。
考え方: MainActorはUIに関係する仕事を同じactor境界へまとめる。

重要ポイント:
- @MainActorで型/関数/propertyを隔離。
- SwiftUI/UIKitのUI更新と関係。
- 重いwork全部をMainActorで行わない。
- MainActor.runを使う場合も。

コード:
```swift
@MainActor
final class ViewModel{
 var title=""
 func update(_ v:String){title=v}
}
```

なぜ重要か: Swift 6 strict concurrencyでUI state更新errorを理解するために必須。
注意: MainActorをmain threadという低level概念だけで覚えない。

確認問題:
Q1. @MainActorの意味は？ [Intermediate]
```swift
@MainActor final class VM{var state=0}
```
A. MainActorへisolate
B. new thread固定
C. ARC停止
D. Optional化
正解: A
解説: MainActor isolationを付ける。

詳しい解説:
- 用語・考え方: MainActor は「メインスレッドで実行される」特別な actor です。型やメソッドに `@MainActor` を付けると、その中の処理はメインスレッド上で行われることが保証されます。UI の更新はメインスレッドから行う必要があるため、画面に関わる型でよく使われます。
- 正解になる理由: @MainActor は隔離先を MainActor に指定する印です。付けた型のプロパティやメソッドへは、外部から await 付きでアクセスすることになります。
- 他の選択肢 new thread固定: 新しいスレッドを作る指定ではありません。既存のメインスレッドで動かす指定です。
- 他の選択肢 ARC停止: メモリ管理は通常どおり働きます。
- 他の選択肢 Optional化: 値の有無を表す Optional とは無関係です。
- 覚えておくこと: @MainActor はメインスレッドでの実行を保証する。

Q2. 重いCPU処理をMainActorで行う問題は？ [Intermediate]
```swift
@MainActor func heavy(){...}
```
A. UI responsiveness悪化
B. 必ず高速化
C. 通信暗号化
D. 問題なし
正解: A
解説: MainActorを長時間占有する。

詳しい解説:
- 用語・考え方: メインスレッドは画面の描画とユーザー操作の受け付けを担当します。ここで時間のかかる計算を行うと、その間は描画も入力処理も進まず、画面が固まったように見えます。重い処理は MainActor の外へ出し、結果を受け取るときだけメインに戻すのが基本です。
- 正解になる理由: MainActor を長時間占有すると、UI の応答性が損なわれます。計算そのものが速くなるわけでもありません。
- 他の選択肢 必ず高速化: 実行場所を変えても計算量は変わりません。むしろ他の作業を止めてしまいます。
- 他の選択肢 通信暗号化: 通信の保護とは無関係です。
- 他の選択肢 問題なし: 応答性の低下という明確な問題があります。
- 覚えておくこと: 重い処理をメインで回すと画面が固まる。

## 11. Sendable・Strict Concurrency [Intermediate]

概要: 並行境界を越えて安全に渡せる値を型で表す。
考え方: Sendableは『別のConcurrency contextへ渡しても安全か』の契約。

重要ポイント:
- 値型は構成要素次第でSendableになりやすい。
- mutable classは設計が難しい。
- @Sendable closureでcapture安全性を検査。
- Swift 6 modeでdata race診断が強化。

コード:
```swift
struct User:Sendable{
 let id:Int
 let name:String
}
```

なぜ重要か: actor/Task境界のcompiler errorを理解するために必要。
注意: @unchecked Sendableをerror消し目的で使わない。

確認問題:
Q1. Sendableが表すものは？ [Intermediate]

struct Value:Sendable{}

D. Hashable同義

- 正解になる理由: コンパイラはこの契約をもとに、危険な受け渡しを警告やエラーとして指摘します。実行してみるまで分からなかったデータ競合を、ビルド時に見つけられるようになります。

- 他の選択肢 View描画: 画面表示とは無関係です。
- 他の選択肢 Hashable同義: Hashable は hash 値と等価比較の契約で、目的がまったく異なります。
- 覚えておくこと: Sendable は「並行の境界を越えて渡して安全」の証明。

Q2. @unchecked Sendableを慎重にする理由は？ [Intermediate]
```swift
final class Box:@unchecked Sendable{}
```
A. 安全性保証を自分で引き受ける
B. compile不可
C. UIKit専用
D. 遅い
正解: A
解説: compilerの一部確認を開発者責任で迂回する。

詳しい解説:

- 正解になる理由: 保証が誤っていても、コンパイラは警告してくれません。データ競合は再現しにくく発見が難しいため、安易に付けると原因究明が困難な不具合につながります。
- 他の選択肢 compile不可: コンパイル自体は通ります。通ってしまうことこそが注意すべき点です。
- 他の選択肢 UIKit専用: 特定の UI フレームワーク専用の仕組みではありません。
- 他の選択肢 遅い: 実行速度が落ちる指定ではありません。
- 覚えておくこと: @unchecked は検査の免除。安全性の責任を自分で負う。

## 12. Continuation・Callback Bridge [Intermediate]

概要: completion handler型APIをasync/awaitへ橋渡しする。
考え方: Continuationは『後でここからasync関数を再開する』ための橋。

重要ポイント:
- withCheckedContinuation系。
- resumeは原則1回。
- returning/throwingで結果返却。
- 既にasync APIがあるなら無理にwrapしない。

コード:
```swift
func load() async throws -> Data{
 try await withCheckedThrowingContinuation{c in
  legacyLoad{result in c.resume(with:result)}
 }
}
```

なぜ重要か: 古いUIKit/SDKのcallback APIとmodern Concurrencyをつなぐ。
注意: resume漏れや複数resumeは重大bug。

確認問題:
Q1. Continuationの代表用途は？ [Intermediate]
```swift
withCheckedContinuation{c in ...}
```
A. callback APIをasyncへbridge
B. Array sort
C. Auto Layout
D. Codable合成
正解: A
解説: callback形式をasyncへ変換する。

詳しい解説:
- 用語・考え方: 既存の API には、完了時にクロージャを呼び出す形式（コールバック）のものが数多くあります。Continuation は、そうした API を async/await の形へ橋渡しする仕組みです。`withCheckedContinuation` の中でコールバックを受け取り、`resume` で結果を返すと、呼び出し側は普通の await として書けます。
- 正解になる理由: 古い形式の API を、新しい非同期の書き方の中へ自然に取り込めます。呼び出し側のコードをコールバックの入れ子にせずに済みます。
- 他の選択肢 Array sort: 並べ替えとは無関係です。
- 他の選択肢 Auto Layout: 画面のレイアウトとは無関係です。
- 他の選択肢 Codable合成: データ変換の自動生成とは無関係です。
- 覚えておくこと: Continuation はコールバック API を await の形に変換する。

Q2. resumeの重要ruleは？ [Intermediate]
```swift
c.resume(returning:value)
```
A. 原則ちょうど1回
B. 何回でも
C. 呼ばなくてよい
D. main thread限定
正解: A
解説: async処理を正しく完了させるため1回resumeする。

詳しい解説:
- 用語・考え方: resume は「待っていた処理を再開させる」呼び出しです。再開は 1 回きりの出来事なので、ちょうど 1 回だけ呼ぶ必要があります。1 度も呼ばないと処理が永久に再開されず、2 回以上呼ぶと不正な状態になります。
- コードの流れ: await している処理が、Continuation を受け取って中断する。
- コードの流れ: コールバックが呼ばれたら resume で結果を渡し、処理を再開させる。
- コードの流れ: resume を呼ばないと、その処理はいつまでも再開されない。
- コードの流れ: 2 回呼ぶと、すでに再開済みの処理をもう一度再開しようとして不正になる。
- 正解になる理由: `withCheckedContinuation` の checked は、この規則の違反を実行時に検出してくれることを意味します。コールバックが複数回呼ばれる API を橋渡しするときは特に注意が必要です。
- 他の選択肢 何回でも: 複数回の呼び出しは規則違反です。checked 版では実行時に検出されます。
- 他の選択肢 呼ばなくてよい: 呼ばなければ再開されず、処理が止まったままになります。
- 他の選択肢 main thread限定: 特定のスレッドからの呼び出しに限定されてはいません。
- 覚えておくこと: resume はちょうど 1 回。0 回でも 2 回でも壊れる。
