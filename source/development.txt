## 01. Xcode：Project・Target・Scheme・Build Configuration [Beginner]

概要: Xcodeの設定単位を区別し、どこを変更しているのか理解する。
考え方: Projectは入れ物、Targetは製品、Schemeは実行/テストの組み合わせ、ConfigurationはDebug/Release等の設定set。

重要ポイント:
- Projectは複数Targetを含められる。
- TargetごとにBundle ID/Build Settings/Capabilities。
- SchemeでRun/Test/Profileを構成。
- Debug/Releaseで設定や最適化を分ける。

コード:
```swift
// Project -> Target -> Build Settings
// Scheme -> Run / Test / Profile -> Configuration
```

なぜ重要か: Xcode errorの多くは『どのTarget/Schemeか』を理解すると追いやすい。
注意: ProjectとTargetを混同すると変更が反映されない原因になる。

確認問題:
Q1. Bundle Identifierを主に持つ単位は？ [Beginner]
```swift
Project -> Target -> General
```
A. Target
B. Git branch
C. Function
D. Array
正解: A
解説: app Targetごとに製品設定を持つ。

詳しい解説:
- 用語・考え方: Xcode の Project は入れ物で、その中の Target が「実際に作られる 1 つの成果物」（アプリ本体、テスト、拡張機能など）を表します。Bundle Identifier は成果物を一意に識別する文字列なので、Target 単位で持ちます。
- 正解になる理由: アプリ本体とテストとウィジェットは別々の成果物なので、それぞれ別の Bundle Identifier を持ちます。設定は Target ごとに管理されます。
- 他の選択肢 Git branch: ソースコードの履歴を分ける仕組みで、成果物の設定とは無関係です。
- 他の選択肢 Function: コードの中の処理の単位で、アプリの識別子とは関係ありません。
- 他の選択肢 Array: 値を並べて持つデータ型です。
- 覚えておくこと: 成果物の単位が Target。識別子は Target ごと。

Q2. Schemeが主に決めるものは？ [Beginner]
```swift
Run / Test / Profile
```
A. どのTarget/Configurationで実行するか
B. JSON key
C. 継承
D. HTTP status
正解: A
解説: Run/Test/Profile等のactionを構成する。

詳しい解説:
- 用語・考え方: Scheme は「何を、どの設定で、どう動かすか」をまとめた実行手順です。どの Target をビルドするか、Debug と Release のどちらの Build Configuration を使うか、Run / Test / Profile それぞれで何をするかを持ちます。
- 正解になる理由: Target が成果物、Configuration が設定の組、Scheme がその組み合わせと実行方法を束ねる、という役割分担です。
- 他の選択肢 JSON key: データ形式のキー名で、ビルド設定とは無関係です。
- 他の選択肢 継承: 型どうしの関係であり、ビルドの構成とは別です。
- 他の選択肢 HTTP status: 通信の応答を表す番号です。
- 覚えておくこと: Scheme は「どの Target をどの設定で動かすか」の束。

## 02. Compiler Error・Warning・Fix-it [Beginner]

概要: error messageを修正指示ではなく、型と文脈の手掛かりとして読む。
考え方: 最初のerrorが原因で後続errorが大量に出ることがある。

重要ポイント:
- errorとwarningを区別。
- 最初の意味あるerrorから確認。
- expected/found type、scope、access levelを見る。
- Fix-itは意味を理解して適用。

コード:
```swift
let count:Int="3"
// Cannot convert value of type String to specified type Int
```

なぜ重要か: AIに丸投げせず原因を限定できる基礎。
注意: error文を読まずにrandom修正しない。

確認問題:
Q1. 大量error時まず見る候補は？ [Beginner]
```swift
// 20 errors
```
A. 最初の根本error
B. 最後のwarningだけ
C. 全部無視
D. Cleanだけ
正解: A
解説: 1つのsyntax/type errorが後続解析を崩す場合がある。

詳しい解説:
- 用語・考え方: コンパイラは 1 つの誤りを見つけた後も解析を続けようとするため、根本原因から派生した二次的なエラーが大量に出ることがあります。特に括弧の閉じ忘れや型の食い違いは、以降の解釈をすべて狂わせます。
- 正解になる理由: 最初のエラーが根本原因であることが多く、それを直すと後続のエラーがまとめて消えることがよくあります。上から順に、1 つ直しては再ビルドするのが速い進め方です。
- 他の選択肢 最後のwarningだけ: 警告は重要な手がかりになることもありますが、ビルドを止めているのはエラーです。まずエラーを解消します。
- 他の選択肢 全部無視: エラーを無視するとビルド自体が完了しません。
- 他の選択肢 Cleanだけ: クリーンビルドが有効な場面もありますが、書いたコード自体の誤りは消えません。
- 覚えておくこと: エラーは上から 1 つずつ。根本原因が派生エラーを量産する。

Q2. Fix-itの扱いは？ [Beginner]
```swift
// Xcode suggests a fix
```
A. 意味を理解して適用
B. 必ず全部適用
C. 絶対使わない
D. Git削除
正解: A
解説: 候補なので意図を理解して使う。

詳しい解説:
- 用語・考え方: Fix-it はコンパイラが提案する修正候補です。多くの場合は妥当ですが、あくまで「型の辻褄を合わせる」提案であり、書き手の意図まで理解しているわけではありません。
- 正解になる理由: たとえば Optional の扱いで `!` を付ける提案が出ることがありますが、それは型を通すだけで、nil のときに停止する危険は残ります。提案の意味を理解してから適用します。
- 他の選択肢 必ず全部適用: 無条件に適用すると、意図と違う修正が入り、別の不具合の原因になります。
- 他の選択肢 絶対使わない: 有用な提案も多いため、使わないと決める必要はありません。
- 他の選択肢 Git削除: バージョン管理の操作とは無関係です。
- 覚えておくこと: Fix-it は提案。意味を理解してから適用する。

## 03. Module・import・File Organization [Basic]

概要: Swift codeの可視性とFile/Module境界を理解する。
考え方: Fileは整理単位、Moduleはcompile/import境界。

重要ポイント:
- importで他Moduleの公開API利用。
- 同一Target内は通常同一Module。
- 型/責務ごとにFile分割。
- Access ControlはModule境界と関係。

コード:
```swift
import Foundation
import SwiftUI
```

なぜ重要か: Package分割やtest Targetで『見える/見えない』を理解できる。
注意: Fileを分けただけでは別Moduleにならない。

確認問題:
Q1. 同一app Target内のSwift Fileは通常？ [Basic]
```swift
// App target
```
A. 同じModule
B. 必ず別Module
C. 同じclass
D. Git submodule
正解: A
解説: 通常Targetがcompile module単位。

詳しい解説:
- 用語・考え方: Module はコンパイルとアクセス制御の単位です。通常は 1 つの Target が 1 つの Module になり、その中の Swift ファイルどうしは import なしで互いを参照できます（既定の internal で見えるため）。
- 正解になる理由: 同じ Target のファイルは同じ Module に属するため、他のファイルで定義した型をそのまま使えます。別 Module のものを使うときだけ import が必要です。
- 他の選択肢 必ず別Module: ファイルごとに Module が分かれることはありません。
- 他の選択肢 同じclass: ファイルと型は別の概念です。1 ファイルに複数の型を書けます。
- 他の選択肢 Git submodule: バージョン管理上の仕組みで、コンパイル単位とは別です。
- 覚えておくこと: 通常は Target = Module。同じ Module 内は import 不要。

Q2. importの目的は？ [Basic]
```swift
import Foundation
```
A. 他Moduleの公開APIを利用
B. Git commit
C. DB migration
D. UI layout
正解: A
解説: Moduleの公開宣言を使えるようにする。

詳しい解説:
- 用語・考え方: import は「別の Module が公開している API を、このファイルから使えるようにする」宣言です。公開されていない（internal 以下の）宣言は import しても見えません。
- 正解になる理由: Foundation や SwiftUI のような外部 Module の機能を使うには import が必要です。逆に言えば、import 行を見ればそのファイルが何に依存しているかが分かります。
- 他の選択肢 Git commit: バージョン管理の操作とは無関係です。
- 他の選択肢 DB migration: データベースの構造変更とは無関係です。
- 他の選択肢 UI layout: 画面配置とは無関係です。
- 覚えておくこと: import は他 Module の公開 API を使うための宣言。

## 04. Swift Package Manager・Package.swift [Basic]

概要: 外部依存と自作ModuleをPackageとして管理する。
考え方: Packageはcodeを再利用可能なModuleとして切り出し、依存を明示する仕組み。

重要ポイント:
- Package.swiftにproduct/target/dependency。
- Library/Executable等product。
- Target間依存を明示。
- XcodeからPackage Dependency追加可能。

コード:
```swift
// Package.swift
let package = Package(
 name:"CoreKit",
 products:[.library(name:"CoreKit",targets:["CoreKit"])],
 targets:[.target(name:"CoreKit"),.testTarget(name:"CoreKitTests",dependencies:["CoreKit"])]
)
```

なぜ重要か: library導入、自作共通層、test可能なModule分割で必須。
注意: 依存を増やしすぎると更新/security/build costが増える。

確認問題:
Q1. SwiftPM manifestは？ [Basic]
```swift
// package definition
```
A. Package.swift
B. Podfileだけ
C. Info.plist
D. README
正解: A
解説: Package.swiftでpackage構成を定義。

詳しい解説:
- 用語・考え方: Swift Package Manager では、パッケージの構成を Package.swift というファイルに Swift のコードとして書きます。名前、対応プラットフォーム、依存パッケージ、Target の構成などをここで宣言します。
- 正解になる理由: 設定ファイルが Swift コードなので、型チェックが効き、補完も使えます。この 1 ファイルがパッケージの定義そのものです。
- 他の選択肢 Podfileだけ: 別の依存管理ツールで使う設定ファイルです。SwiftPM の manifest ではありません。
- 他の選択肢 Info.plist: アプリの実行時設定を書くファイルで、パッケージ構成の定義ではありません。
- 他の選択肢 README: 人向けの説明文書であり、ビルドには使われません。
- 覚えておくこと: SwiftPM の設定は Package.swift。

Q2. testTargetのdependency例は？ [Basic]
```swift
.testTarget(name:"CoreTests",dependencies:["Core"])
```
A. test対象Target
B. Git remote
C. Simulator
D. Bundle IDだけ
正解: A
解説: test対象moduleをdependencyにする。

詳しい解説:
- 用語・考え方: テスト用の Target は、検証したいコードを import して使う必要があります。そのため Package.swift の testTarget では、テスト対象の Target を dependencies に指定します。
- 正解になる理由: 依存として宣言することで、テストコードから対象 Module の公開 API を呼べるようになります。宣言しなければ import できません。
- 他の選択肢 Git remote: コードの置き場所の話であり、ビルド時の依存関係ではありません。
- 他の選択肢 Simulator: 実行環境であって、ビルドの依存対象ではありません。
- 他の選択肢 Bundle IDだけ: 成果物の識別子であり、依存関係の指定ではありません。
- 覚えておくこと: testTarget はテスト対象 Target に依存させる。

## 05. Dependency Version・Lock・Supply Chain [Intermediate]

概要: 外部Packageを安全に導入・更新する考え方を学ぶ。
考え方: 依存追加は、その更新・脆弱性・互換性も引き受けること。

重要ポイント:
- version requirementを理解。
- Package.resolvedで解決versionを再現。
- repository/maintainer/licenseを確認。
- 必要性が低い依存を増やさない。

コード:
```swift
// Review repository, version rule, license, maintenance
```

なぜ重要か: 実務ではlibrary選定自体が設計判断。
注意: 人気だけで安全とは限らない。

確認問題:
Q1. Package.resolvedの主目的は？ [Intermediate]
```swift
Package.resolved
```
A. 依存versionの再現性
B. UI色
C. Keychain保存
D. HTTP body
正解: A
解説: 解決versionを記録する。

詳しい解説:
- 用語・考え方: Package.swift には「1.2.0 以上」のような範囲で依存を書くことが多いため、解決される実際のバージョンは時期によって変わり得ます。Package.resolved は、実際に選ばれたバージョンを記録しておくファイルです。
- 正解になる理由: これをリポジトリに含めておくと、他の開発者や CI がまったく同じバージョンでビルドできます。「自分の環境では動く」という食い違いを防げます。
- 他の選択肢 UI色: 見た目の設定とは無関係です。
- 他の選択肢 Keychain保存: 資格情報の保存とは無関係です。
- 他の選択肢 HTTP body: 通信内容とは無関係です。
- 覚えておくこと: Package.resolved は解決済みバージョンの記録＝再現性。

Q2. 外部Package導入時に見るべきものは？ [Intermediate]
```swift
// dependency review
```
A. 必要性・更新状況・license・security
B. 星数だけ
C. README色
D. 作者icon
正解: A
解説: 保守/security costも評価する。

詳しい解説:
- 用語・考え方: 外部パッケージの導入は、機能を得る代わりに保守の負担とリスクも引き受ける決定です。更新が止まっていないか、ライセンスが自分の用途に合うか、脆弱性への対応があるか、そもそも自分で書けない規模かを検討します。
- 正解になる理由: 依存は増えるほど、ビルド時間・アップデート追従・セキュリティ対応の負担が増えます。人気だけでは判断材料になりません。
- 他の選択肢 星数だけ: 人気の指標にはなりますが、更新状況やライセンス適合を保証しません。
- 他の選択肢 README色: 見た目は品質と無関係です。
- 他の選択肢 作者icon: 作者の見た目は判断材料になりません。
- 覚えておくこと: 依存は資産でなく負債にもなる。必要性・保守・ライセンス・安全性で判断。

## 06. Breakpoint・LLDB・Step実行 [Basic]

概要: 実行中の状態を止めて観察し、原因を推測ではなく確認する。
考え方: Debuggerは『その瞬間の真実を見る』道具。

重要ポイント:
- breakpointで停止。
- step over/into/out。
- Variables Viewで値確認。
- LLDBのpo/pで式評価。

コード:
```swift
// Breakpoint
// po user
// p count
```

なぜ重要か: bug解析をprintだけに依存しないための基本。
注意: breakpointを置く前に何の仮説を確認するか考える。

確認問題:
Q1. Step Intoの意味は？ [Basic]
```swift
someFunction()
```
A. 関数内部へ入る
B. 次行だけ
C. app終了
D. Git push
正解: A
解説: 呼び出し先内部へ進む。

詳しい解説:
- 用語・考え方: デバッガの実行制御には、Step Over（現在の行を実行して次の行へ）、Step Into（その行で呼んでいる関数の中へ入る）、Step Out（今の関数を抜けるまで進む）があります。
- 正解になる理由: Step Into は呼び出し先の内部で何が起きているかを追うための操作です。原因が自分の書いた関数の中にあるときに使います。
- 他の選択肢 次行だけ: 現在の行を実行して次の行へ進むのは Step Over です。呼び出し先の中には入りません。
- 他の選択肢 app終了: 実行を終了する操作ではありません。
- 他の選択肢 Git push: バージョン管理の操作とは無関係です。
- 覚えておくこと: Step Into は呼び出し先の内部へ。Step Over は入らない。

Q2. LLDBのpoでよくすることは？ [Basic]
```swift
po object
```
A. object情報を表示
B. package更新
C. 署名
D. Auto Layout
正解: A
解説: 停止中の値を確認する。

詳しい解説:
- 用語・考え方: LLDB はデバッガで、ブレークポイントで停止しているときにコマンドを打てます。`po`（print object）は式を評価して、その値の説明を表示します。停止している時点の実際の値を確認できます。
- 正解になる理由: print を仕込んで再ビルドしなくても、止まっている場所で値を調べられます。仮説の検証を素早く回せます。
- 他の選択肢 package更新: 依存パッケージの更新はビルド設定側の操作です。
- 他の選択肢 署名: 配布のための署名とは無関係です。
- 他の選択肢 Auto Layout: 画面配置の調整とは無関係です。
- 覚えておくこと: po は停止中の値を確認するコマンド。

## 07. Logger・OSLog・Debug Print [Basic]

概要: 診断情報を適切なlevelとprivacyで記録する。
考え方: Logは後で何が起きたか再現する観測点。

重要ポイント:
- Loggerでcategory/subsystem。
- debug/info/notice/error/fault等。
- secret/個人情報をlogしない。
- productionで必要な観測点を設計。

コード:
```swift
import OSLog
let logger=Logger(subsystem:"com.example.app",category:"network")
logger.info("Request completed")
```

なぜ重要か: 実機だけの問題や非同期bug解析に役立つ。
注意: token/password/個人情報をlogしない。

確認問題:
Q1. Loggerのcategoryを分ける利点は？ [Basic]
```swift
Logger(subsystem:"...",category:"network")
```
A. 機能別に検索しやすい
B. 必ず高速
C. ARC制御
D. JSON encode
正解: A
解説: network/database等で分類できる。

詳しい解説:
- 用語・考え方: Logger は subsystem（どのアプリ・コンポーネントか）と category（どの機能か）でログを分類できます。分類しておくと、大量のログの中から目的の領域だけを絞り込めます。
- 正解になる理由: network、database、ui のように category を分けておくと、不具合の調査時に該当領域のログだけを追えます。print と違い、後から絞り込める点が実務では効きます。
- 他の選択肢 必ず高速: 分類は検索性のためであり、実行速度のためではありません。
- 他の選択肢 ARC制御: メモリ管理とは無関係です。
- 他の選択肢 JSON encode: データ変換とは無関係です。
- 覚えておくこと: category はログを後から絞り込むための分類。

Q2. logへ出してはいけない代表例は？ [Basic]
```swift
logger.debug("token=...")
```
A. 認証token/password
B. 処理開始
C. error種別
D. 件数
正解: A
解説: 秘密情報漏洩につながる。

詳しい解説:
- 用語・考え方: ログは端末に残り、クラッシュレポートや解析基盤へ送られることもあります。開発中に見たい情報と、外部に出てはいけない情報は区別する必要があります。認証情報や個人情報はログに残すべきではありません。
- 正解になる理由: トークンやパスワードがログに出ると、端末を調べられた場合やレポート経由で漏れる可能性があります。開発者向けのログと、利用者に見せるエラーメッセージも別物として設計します。利用者には次の行動が分かる表現を、開発者向けには原因究明に必要な情報を残します。
- 他の選択肢 処理開始: 処理の開始・終了は流れを追うのに有用で、秘密情報ではありません。
- 他の選択肢 error種別: エラーの種類は原因究明に必要な情報です。
- 他の選択肢 件数: 件数のような統計値は通常問題ありません。
- 覚えておくこと: 資格情報はログに出さない。開発用ログと利用者向け表示は別物。

## 08. Instruments・Memory Graph・Sanitizer [Intermediate]

概要: 性能・memory・競合を専用toolで測定する。
考え方: 『遅い気がする』ではなく、計測してbottleneckを特定する。

重要ポイント:
- Time ProfilerでCPU。
- Allocations/Leaksでmemory。
- Memory Graphで参照循環。
- Thread Sanitizerでdata race検出を支援。

コード:
```swift
// Product > Profile
// Time Profiler / Allocations / Leaks / Memory Graph
```

なぜ重要か: 中級以降は実行特性を測れることが重要。

## 09. Swift Testing：@Test・#expect・#require [Basic]

概要: Swift Testingで小さな単体testを書く。

確認問題:
Q1. Swift Testingの期待Macroは？ [Basic]
```swift

```

B. #if
C. #selector
D. #available

解説: #expectで条件を検証。

詳しい解説:
- 用語・考え方: Swift Testing では `@Test` を付けた関数がテストになり、`#expect(条件)` で条件の成立を検証します。#expect は macro なので、失敗時に式の中身を分解して「何が何と等しくなかったか」を示せます。
- 正解になる理由: 検証の中心となる記法が #expect です。失敗しても以降の行は続けて実行されるため、1 回の実行で複数の問題を見つけられます。

- 他の選択肢 #available: 実行環境の対応状況を判定する条件で、テストの検証とは別です。
- 覚えておくこと: 検証は #expect。

Q2. #requireの用途は？ [Basic]

B. 通信開始
C. UI layout
D. ARC retain

- 正解になる理由: 前提が崩れた状態で続けると、無関係な失敗が大量に出て原因が分かりにくくなります。#expect が「記録して続行」、#require が「そこで打ち切り」と使い分けます。
- 他の選択肢 通信開始: 通信の開始とは無関係です。
- 他の選択肢 UI layout: 画面配置とは無関係です。
- 他の選択肢 ARC retain: メモリ管理とは無関係です。
- 覚えておくこと: #expect は続行、#require は前提が崩れたら打ち切り。

## 12. Dependency Injection・Test Double [Intermediate]

概要: 外部依存を差し替え可能にし、testしやすい設計を作る。
考え方: 依存を内部で勝手に生成せず外から渡すと、何に依存するかが見える。

重要ポイント:
- initializer injectionがsimple。
- Protocolでservice境界を表す場合。
- Stub/Fake/Mock等。
- global singleton依存を減らす。

コード:
```swift
protocol UserRepository{func load() async throws -> User}
final class VM{
 let repo:any UserRepository
 init(repo:any UserRepository){self.repo=repo}
}
```

なぜ重要か: networkなしでlogicをtestし実装交換を容易にする。
注意: Protocolを作ること自体がDIではない。

確認問題:
Q1. Initializer Injectionの利点は？ [Intermediate]
```swift
init(repository:UserRepository)
```
A. 依存が明示され差し替えやすい
B. 必ずSingleton
C. UI自動生成
D. ARC不要
正解: A
解説: test doubleへ置換しやすい。

詳しい解説:
- 用語・考え方: Dependency Injection は、必要なものを内部で自分で作るのではなく、外から渡してもらう設計です。イニシャライザで受け取る形（Initializer Injection）にすると、その型が何に依存しているかが宣言を見るだけで分かります。
- 正解になる理由: 依存が引数として現れるため、テスト時には本物の代わりに制御可能な実装を渡せます。内部で直接 URLSession を作っていると差し替えられません。
- 他の選択肢 必ずSingleton: むしろ共有インスタンスへの直接依存を避ける手段です。Singleton を強制しません。
- 他の選択肢 UI自動生成: 画面が自動生成されることはありません。
- 他の選択肢 ARC不要: メモリ管理は通常どおり必要です。
- 関連例:
```swift
protocol UserLoading {
    func load() -> String
}
struct APIUserLoader: UserLoading {
    func load() -> String { "from API" }
}
struct StubUserLoader: UserLoading {
    func load() -> String { "stub" }
}
struct ViewModel {
    let loader: UserLoading
    func title() -> String { "User: \(loader.load())" }
}
print(ViewModel(loader: APIUserLoader()).title())
print(ViewModel(loader: StubUserLoader()).title())
```
- 関連例の出力: User: from API
User: stub
- 関連例の説明: ViewModel のコードは一切変えずに、渡す実装だけを差し替えています。テストでは StubUserLoader を渡せば、通信なしで結果を固定できます。
- 覚えておくこと: 依存は外から渡す。差し替えられることがテスト容易性になる。

Q2. Test Doubleの目的は？ [Intermediate]
```swift

```
A. 外部依存を制御可能な代替へ置換
B. production APIを必ず呼ぶ
C. Git操作
D. 署名
正解: A
解説: testでnetwork/DBの不確定要素を制御する。

詳しい解説:
- 用語・考え方: Test Double は、テスト中に本物の代わりに使う代替実装の総称です（Stub、Mock、Fake など）。通信・データベース・時刻のように、結果が外部要因で変わるものを固定し、テストの結果を安定させます。
- 正解になる理由: 本物の API を呼ぶと、ネットワーク状況やサーバー側のデータで結果が変わり、失敗の原因がコードなのか環境なのか判別できません。代替に差し替えれば、検証したい条件だけを再現できます。

- 他の選択肢 Git操作: バージョン管理の操作とは無関係です。
- 他の選択肢 署名: 配布時の署名とは無関係です。
- 覚えておくこと: 外部要因を固定し、検証したい条件を再現するための代替実装。

## 17. SwiftData：Schema・Migration・Data Evolution [Intermediate]

概要: release後にdata modelを変更する責任を理解する。
考え方: schema変更はcode変更だけでなく、既存user dataを新しい形へ移す問題。

重要ポイント:
- property rename/type change/deleteはmigration影響。
- VersionedSchema等を使う場面。
- 軽量migrationで済む変更も。
- 本番dataを壊さないtestが必要。

コード:
```swift
// v1: name
// v2: displayName
// existing store must remain readable
```

なぜ重要か: 永続化appを継続運用するなら必須。
注意: 開発中のstore削除を本番migration代わりにしない。

確認問題:
Q1. release後のschema変更で最重要なのは？ [Intermediate]
```swift
// existing user data
```
A. 既存dataをどう移行するか
B. Xcode theme
C. Git username
D. UI色
正解: A
解説: 既存storeの安全なmigrationが必要。

詳しい解説:
- 用語・考え方: リリース後は、利用者の端末に既存のデータが存在します。モデルの構造（schema）を変えると、古い形式で保存されたデータをどう読み替えるかを決めておかなければ、アプリが起動できなくなったりデータを失ったりします。
- 正解になる理由: 設計時に考えるべきは「新しい形をどう定義するか」だけでなく「既存データをどう移行するか」です。移行の道筋が無い変更は利用者のデータを壊します。
- 他の選択肢 Xcode theme: 開発環境の見た目の設定であり、利用者のデータとは無関係です。
- 他の選択肢 Git username: バージョン管理の設定であり、無関係です。
- 他の選択肢 UI色: 画面の配色であり、データ移行とは無関係です。
- 覚えておくこと: schema 変更の主題は既存データの移行。

Q2. store削除が本番migrationの代わりになる？ [Intermediate]
```swift
// delete app data
```
A. ならない
B. 完全に同じ
C. 必ず推奨
D. SwiftDataはmigration不要
正解: A
解説: user dataを消せないためmigration設計が必要。

詳しい解説:
- 用語・考え方: 開発中は、保存領域を削除して作り直せば新しい schema で動きます。しかし本番では、その操作は利用者のデータを消すことに直結します。移行処理を設計して、既存データを新しい形へ変換する必要があります。
- 正解になる理由: 利用者のデータは失われてはいけないものなので、削除は代替になりません。開発中の手段をそのまま本番に持ち込まないことが重要です。
- 他の選択肢 完全に同じ: 結果はまったく異なります。片方はデータを保ち、片方は失います。

- 他の選択肢 SwiftDataはmigration不要: 移行は必要です。不要になることはありません。

## 20. Architecture・Git・Security・API Design [Intermediate]

概要: 責務分離、変更管理、安全性を実装と同じレベルで扱う。
考え方: 良い開発は『動くcode』だけでなく、変更可能・検証可能・安全な境界を作る。

重要ポイント:
- View→ViewModel→Repository等で責務分離。
- git status/diff/小さなcommit/PR。
- secret/tokenをcommitしない。
- API名とdocumentationで意図を明確にする。

コード:
```swift
View -> ViewModel -> Repository -> API / DB

git status
git diff
// Never commit secrets
```

なぜ重要か: 個人開発でも規模が増えるほど差が出る。
注意: pattern名を守ることより、責務・依存方向・安全境界が明確かを見る。

確認問題:
Q1. 責務分離の目的は？ [Intermediate]
```swift
View -> ViewModel -> Repository
```
A. 変更影響を局所化しtestしやすくする
B. file数を増やすだけ
C. 必ず高速
D. Protocol最大化
正解: A
解説: 依存方向と責務を整理する。

詳しい解説:
- 用語・考え方: 責務分離は、それぞれの部分が「1 つのことだけを担当する」ように分ける設計です。画面表示、データ取得、業務ロジックが混ざっていると、1 か所の変更が全体に波及し、テストも全体を起動しないと書けません。
- 正解になる理由: 境界を引くと、変更の影響がその内側に留まり、依存を差し替えて部分だけをテストできるようになります。ファイル数は結果として増えることもありますが、それ自体は目的ではありません。
- 他の選択肢 file数を増やすだけ: 分割はファイル数を増やすこと自体が目的ではありません。増えても整理されていなければ意味がありません。
- 他の選択肢 必ず高速: 速度が上がる保証はありません。目的は変更のしやすさです。
- 他の選択肢 Protocol最大化: 抽象化は必要な箇所に絞るべきで、増やすほど良いわけではありません。過剰な抽象化は読みにくさを生みます。
- 覚えておくこと: 境界を引く目的は、影響の局所化とテスト容易性。

Q2. repositoryへcommitしてはいけないものは？ [Intermediate]
```swift
API_SECRET=...
```
A. secret/token/private key
B. README
C. test名
D. public model
正解: A
解説: 履歴に残るためsecretをcommitしない。

詳しい解説:
- 用語・考え方: commit はローカルの履歴に変更を記録する操作、push はその履歴をリモートへ公開する操作です。重要なのは、commit した時点でその内容が履歴に残るという点で、後のコミットで削除しても過去の履歴からは取り出せてしまいます。
- コードの流れ: 秘密情報を含むファイルを commit すると、その内容が履歴として残る。
- コードの流れ: 後で削除して commit しても、削除前のコミットには内容が残っている。
- コードの流れ: push すると、その履歴ごとリモートへ共有される。
- コードの流れ: 取り除くには履歴の書き換えが必要になり、共有済みなら流出は取り消せない。
- 正解になる理由: 履歴に残る性質があるため、そもそも入れないことが唯一確実な対策です。設定ファイルは .gitignore で除外し、値は環境変数や安全な保管先から与えます。漏れてしまった場合は、削除より先に該当する資格情報を無効化して差し替えます。
- 他の選択肢 README: 説明文書はリポジトリに含めるべきものです。
- 他の選択肢 test名: テストコードは共有して価値のあるものです。
- 他の選択肢 public model: 公開してよいモデル定義は通常のソースコードです。
- 覚えておくこと: commit した時点で履歴に残る。秘密情報は最初から入れない。
