# Foundation & Data

Codable、JSON、Date、URL、HTTP、URLSession、File、UserDefaults、Regex、データモデリングなど実アプリのデータ処理を学ぶ。

このファイルは人が読みやすい教材原本です。構造化データは content.json、完成版は index.html です.

## 01. Equatable・Hashable・Comparable・Identifiable [Basic]

概要: データ型が『比較できる・Set/Dictionaryで使える・順序比較できる・IDを持つ』能力を表す。
考え方: 標準Protocol準拠は、型が何を保証するかを宣言すること。

重要ポイント:
- Equatableで==比較。
- HashableでSet要素やDictionary Key。
- Comparableで大小比較とsorted。
- Identifiableで安定したid。

コード:
```swift
struct User:Identifiable,Hashable{
 let id:UUID
 let name:String
}
```

なぜ重要か: SwiftUI List、cache、重複排除、sortで頻出。
注意: Hashableのidentityに関わる値を不適切に変更する設計は避ける。

確認問題:
Q1. Dictionary Keyに必要な代表Protocolは？ [Basic]
```swift
struct Key: /* ? */ {}
```
A. Hashable
B. View
C. Error
D. Actor
正解: A
解説: Dictionary KeyはHashable。

詳しい解説:
- 用語・考え方: Dictionary はキーから値を素早く探すための型です。探すときはキーの hash 値（値を要約した整数）で候補を絞り、その後 == で本当に同じキーかを確定します。Hashable はこの 2 つの能力をまとめて要求する契約で、Equatable を継承しているため == も使えます。
- 正解になる理由: hash 値の生成と等価比較の両方が揃って初めて、キーによる検索が成立します。String や Int が Key によく使われるのは、これらが標準で Hashable に準拠しているからです。
- 他の選択肢 View: SwiftUI で画面の見た目を表す契約です。データ構造のキー条件とは関係がありません。
- 他の選択肢 Error: throw して投げられる値が満たす契約です。エラー表現のためのもので、検索には使われません。
- 他の選択肢 Actor: 並行処理で可変な状態を保護する型の種類です。キーの条件ではありません。
- 覚えておくこと: Dictionary の Key と Set の要素は Hashable。

Q2. Identifiableが要求する中心propertyは？ [Basic]
```swift
struct Item:Identifiable{...}
```
A. id
B. name
C. hash
D. body
正解: A
解説: 安定したidentifier idを提供する。

詳しい解説:
- 用語・考え方: Identifiable は「この値を一意に識別できる id を持つ」ことを表す契約です。SwiftUI の List や ForEach は、要素の並びが変わったときに「どれが同じ要素か」を id で判断して差分更新を行います。
- 正解になる理由: 要求されるのは id という名前のプロパティ 1 つです。型は Hashable であれば Int でも String でも UUID でも構いません。
- 他の選択肢 name: name は識別子として使えることもありますが、Identifiable が名前として要求するプロパティではありません。同名の別要素があると識別できません。
- 他の選択肢 hash: hash は Hashable が扱う概念です。hash 値は衝突しうるため、一意な識別子としては使えません。
- 他の選択肢 body: body は SwiftUI の View が要求するプロパティで、画面の内容を返します。
- 覚えておくこと: Identifiable が求めるのは id ひとつ。

## 02. Codable・Encodable・Decodable [Basic]

概要: Swift型とJSONなどの外部表現を相互変換する基本を学ぶ。
考え方: Codableは『保存/通信できる形への変換契約』。

重要ポイント:
- Codable=Encodable+Decodable。
- JSONDecoderでData→型。
- JSONEncoderで型→Data。
- propertyがCodableなら自動合成される場合が多い。

コード:
```swift
struct User:Codable{
 let id:Int
 let name:String
}
```

なぜ重要か: REST API、file保存、cacheの中心。
注意: JSONの型やkeyがmodelと合わないとdecode失敗する。

確認問題:
Q1. Codableは何の組み合わせ？ [Basic]
```swift
struct User:Codable{}
```
A. Equatable+Hashable
B. Encodable+Decodable
C. View+Identifiable
D. Error+Sendable
正解: B
解説: CodableはEncodableとDecodableのtypealias。

詳しい解説:
- 用語・考え方: Foundation は Swift 言語そのものには無い「アプリを作るための土台」を提供します。その 1 つが JSON などの外部表現との変換です。Encodable は「Swift の値を外部表現へ書き出せる」、Decodable は「外部表現から Swift の値を作れる」契約で、Codable はその 2 つをまとめた別名（typealias）です。
- 正解になる理由: `typealias Codable = Encodable & Decodable` と定義されているため、Codable と書けば両方向の変換が可能になります。片方だけでよいなら Encodable か Decodable を個別に書けます。
- 他の選択肢 Equatable+Hashable: 等価比較と hash 値生成の契約です。データ変換とは別の目的です。
- 他の選択肢 View+Identifiable: SwiftUI の画面表現と識別の契約で、JSON 変換とは無関係です。
- 他の選択肢 Error+Sendable: エラー表現と並行処理の安全性の契約です。
- 覚えておくこと: Codable = Encodable（書き出し）+ Decodable（読み込み）。

Q2. JSON Data→Userは？ [Basic]
```swift
let user = try /* ? */
```
A. JSONEncoder().encode(User.self)
B. JSONDecoder().decode(User.self,from:data)
C. String(data)
D. User(data)
正解: B
解説: JSONDecoderでDecodable型へdecodeする。

詳しい解説:
- 用語・考え方: JSON の byte 列（Data）から Swift の値を作るのは JSONDecoder の役割です。`decode(User.self, from: data)` は「User という型として data を読み解く」という意味で、第 1 引数に型そのもの（`.self`）、第 2 引数に元データを渡します。データの向きは JSON → Swift です。
- コードの流れ: サーバーなどから受け取った JSON が Data（byte 列）として手元にある。
- コードの流れ: JSONDecoder に「どの型として読むか」と「元の Data」を渡す。
- コードの流れ: 各キーが型のプロパティに対応付けられ、User の値が組み立てられる。
- コードの流れ: 形が合わない場合は例外が投げられるため、呼び出しに try が必要になる。
- 正解になる理由: decode は Decodable な型を作る方向の API です。失敗しうるため try と組み合わせて使います。
- 他の選択肢 JSONEncoder().encode(User.self): JSONEncoder は Swift の値から JSON を作る逆方向の API です。また encode に渡すのは型ではなく値です。
- 他の選択肢 String(data): String(data:encoding:) は byte 列を文字列として解釈するだけで、型のプロパティへの対応付けは行いません。
- 他の選択肢 User(data): User に Data を受け取る初期化が自動で用意されることはありません。自分で定義すれば別ですが、標準の手段ではありません。
- 関連例:
```swift
import Foundation

struct User: Codable { let id: Int; let name: String }

do {
    let encoder = JSONEncoder()
    encoder.outputFormatting = .sortedKeys
    let data = try encoder.encode(User(id: 1, name: "Yuki"))
    print(String(decoding: data, as: UTF8.self))
    let back = try JSONDecoder().decode(User.self, from: data)
    print(back.name)
} catch {
    print("failed")
}
```
- 関連例の出力: {"id":1,"name":"Yuki"}
Yuki
- 関連例の説明: encode で Swift の値 → JSON、decode で JSON → Swift の値と、両方向を 1 つの型で扱えます。sortedKeys はキーの順を安定させる指定です。
- 覚えておくこと: decode は JSON → Swift、encode は Swift → JSON。

## 03. CodingKeys・Custom Codable [Intermediate]

概要: JSON keyとSwift名が違う場合や特殊変換を制御する。
考え方: 外部APIの形と、内部で読みやすいmodel名を無理に一致させなくてよい。

重要ポイント:
- CodingKeysでkey対応。
- decoderのdate strategy等を利用。
- 必要ならinit(from:)を自前実装。
- DTOとDomain Modelを分ける設計も有効。

コード:
```swift
struct UserDTO:Decodable{
 let userID:Int
 enum CodingKeys:String,CodingKey{case userID="user_id"}
}
```

なぜ重要か: snake_case APIや特殊JSONを安全に扱う。
注意: 外部API都合をapp全体のmodelへ漏らさない。

確認問題:
Q1. CodingKeysの役割は？ [Intermediate]
```swift
case userID="user_id"
```
A. Swift名とJSON keyを対応
B. 暗号化
C. Optional化
D. HTTP header
正解: A
解説: 外部key名とSwift property名を対応付ける。

詳しい解説:
- 用語・考え方: JSON のキー名は snake_case（user_id）、Swift のプロパティ名は camelCase（userID）というように、命名規則が食い違うことがよくあります。CodingKeys は「この Swift のプロパティは JSON のこのキーに対応する」という対応表を書くための仕組みです。
- 正解になる理由: `case userID = "user_id"` は、内部では userID、外部の JSON では user_id という名前で扱うことを指定します。これにより Swift 側の命名を崩さずに外部仕様へ合わせられます。
- 他の選択肢 暗号化: CodingKeys は名前の対応付けだけを行い、内容を保護する機能はありません。
- 他の選択肢 Optional化: 値の有無を表す Optional は型の後ろの `?` で指定します。CodingKeys とは別です。
- 他の選択肢 HTTP header: 通信時に付加する情報は URLRequest 側で設定します。データの構造とは別の層です。
- 覚えておくこと: CodingKeys は Swift 名と JSON キー名の対応表。

Q2. DTOをDomain Modelと分ける利点は？ [Intermediate]
```swift
UserDTO -> User
```
A. API変更影響を内部から分離
B. 必ず通信速度倍
C. Codable不要
D. UIKit専用
正解: A
解説: 外部形式との境界を作れる。

詳しい解説:
- 用語・考え方: DTO（Data Transfer Object）は外部とのやり取りの形をそのまま写した型、Domain Model はアプリ内部で扱いやすい形に整えた型です。2 つを分けると、API の仕様変更の影響を変換部分だけに閉じ込められます。
- 正解になる理由: API のキー名や構造が変わっても、修正するのは DTO と変換処理だけで済み、画面やロジックが使う Domain Model は変えずに済みます。境界を 1 か所に集める設計です。
- 他の選択肢 必ず通信速度倍: 型を分けても通信の速さは変わりません。目的は変更の影響範囲を狭めることです。
- 他の選択肢 Codable不要: むしろ DTO 側が Codable に準拠します。Codable が不要になるわけではありません。
- 他の選択肢 UIKit専用: 特定の UI フレームワークとは無関係な設計の話です。
- 覚えておくこと: DTO は外部の形、Domain Model は内部の形。変換点が防波堤になる。

## 04. Data・JSON・Base64 [Basic]

概要: FoundationのDataが生のbyte列を表すことを理解する。
考え方: DataはJSONでも画像でもStringでもなく『byteのまとまり』。

重要ポイント:
- URLSession response bodyでDataを受ける。
- String(data:encoding:)で文字列化可能な場合。
- Base64へ変換可能。
- 内容形式は文脈が必要。

コード:
```swift
let data=Data("Swift".utf8)
let text=String(data:data,encoding:.utf8)
```

なぜ重要か: 通信・file・画像などのI/Oで必須。
注意: Dataだけ見ても中身のformatは分からない。

確認問題:
Q1. Dataが表すものは？ [Basic]
```swift
let data:Data
```
A. byte列
B. 必ずJSON
C. 必ずString
D. View
正解: A
解説: Dataはbyte列。

詳しい解説:
- 用語・考え方: Data は「意味を持たない byte（8 ビットの数値）の並び」を表す型です。JSON も画像もファイルの中身も、通信や保存の場面ではすべて byte 列として扱われます。どう解釈するかは受け取った側が決めます。
- 正解になる理由: Data 自体は中身の種類を知りません。JSON として読むなら JSONDecoder、文字列として読むなら String(decoding:as:)、画像として読むなら画像用の型に渡す、というように解釈方法を指定します。
- 他の選択肢 必ずJSON: JSON はあくまで解釈のしかたの 1 つです。Data には画像や音声も入ります。
- 他の選択肢 必ずString: 文字として解釈できるとは限りません。文字コードを指定して初めて文字列になります。
- 他の選択肢 View: 画面の表現とは無関係です。
- 覚えておくこと: Data は中身を問わない byte 列。解釈は使う側が決める。

Q2. UTF-8 Data→Stringの代表例は？ [Basic]
```swift
String(data:data,encoding:.utf8)
```
A. 正しい
B. 不可
C. JSONDecoder専用
D. UIKit専用
正解: A
解説: encodingを指定してStringとして解釈できる。

詳しい解説:
- 用語・考え方: byte 列を文字列にするには「どの文字コードで解釈するか」を指定する必要があります。同じ byte 列でも UTF-8 と別の符号化方式では違う文字になるためです。`String(data:encoding:)` は解釈に失敗する可能性があるので String? を返します。
- 正解になる理由: encoding に .utf8 を指定することで、byte 列を UTF-8 の文字列として読み解けます。失敗しうる点を踏まえ、if let などで取り出すか、失敗しない `String(decoding:as:)` を使います。
- 他の選択肢 不可: 文字コードを指定すれば変換できます。不可能ではありません。
- 他の選択肢 JSONDecoder専用: JSONDecoder を使わずに単なる文字列として読む用途でも使えます。
- 他の選択肢 UIKit専用: Foundation の API であり、UI フレームワークに限定されません。
- 関連例:
```swift
import Foundation

let data = Data("Gym".utf8)
print(data.count)
if let text = String(data: data, encoding: .utf8) {
    print(text)
}
print(String(decoding: data, as: UTF8.self))
```
- 関連例の出力: 3
Gym
Gym
- 関連例の説明: 文字列 → Data、Data → 文字列の両方向です。String(data:encoding:) は失敗しうるので Optional、String(decoding:as:) は不正な byte を置換文字に変えて必ず成功します。
- 覚えておくこと: byte 列 → 文字列には文字コードの指定が要る。

## 05. Date・Calendar・TimeZone [Basic]

概要: 時刻の一点と、人間のcalendar上の年月日を分けて扱う。
考え方: Dateは絶対時刻、Calendar/TimeZoneは年月日時分へ解釈する規則。

重要ポイント:
- Dateは特定の瞬間。
- Calendarで日付成分の加減算。
- TimeZoneで時差。
- 固定秒数で1日を計算しない。

コード:
```swift
let now=Date()
let tomorrow=Calendar.current.date(byAdding:.day,value:1,to:now)
```

なぜ重要か: 予約、log、締切、calendar UIでdate bugを防ぐ。
注意: 1日は常に86400秒とは限らない。

確認問題:
Q1. Dateが表すものは？ [Basic]
```swift
let now=Date()
```
A. 特定の瞬間
B. 必ず日本時間文字列
C. calendar画面
D. TimeZoneだけ
正解: A
解説: Dateは時間軸上の一点。

詳しい解説:
- 用語・考え方: Date は「時間軸上の一点」、つまり世界共通の特定の瞬間を表す値です。表示用の文字列や、年月日といった暦の情報は含んでいません。同じ Date でも、どの地域・どの暦で見るかによって「何年何月何日何時」は変わります。
- 正解になる理由: Date は瞬間そのもの、Calendar と TimeZone がその瞬間を暦の上でどう読むかを決め、フォーマッタが表示用の文字列を作ります。役割がはっきり分かれています。
- 他の選択肢 必ず日本時間文字列: 表示用の文字列は Date から別途組み立てます。Date 自身は文字列を保持しません。
- 他の選択肢 calendar画面: 画面の部品ではありません。値としての時刻です。
- 他の選択肢 TimeZoneだけ: TimeZone は瞬間を地域の時刻として読むための情報で、Date とは別の型です。
- 覚えておくこと: Date は瞬間の値。表示文字列は別に作る。

Q2. 翌日計算に推奨されるのは？ [Intermediate]
```swift
Calendar.current.date(byAdding:.day,value:1,to:date)
```
A. Calendarで日加算
B. 86400秒固定
C. 文字列+1
D. 計算不可
正解: A
解説: 暦ruleを考慮できる。

詳しい解説:
- 用語・考え方: 暦の上での「翌日」は、必ずしも 24 時間後とは限りません。夏時間の切り替わりがある地域では 23 時間や 25 時間になる日があり、うるう秒や暦の違いも存在します。Calendar はこうした規則を踏まえて日付計算を行います。
- 正解になる理由: `Calendar.current.date(byAdding:.day, value: 1, to:)` は暦の規則に従って翌日を求めます。自分で秒数を足すより安全です。
- 他の選択肢 86400秒固定: 1 日を 86400 秒固定として足す方法は、夏時間のある地域で 1 時間ずれる原因になります。時間の間隔としては正しくても、暦の上の「翌日」とは一致しないことがあります。
- 他の選択肢 文字列+1: 日付を文字列として扱って加算するのは、桁上がりや月末の処理を自前で実装することになり誤りの元です。
- 他の選択肢 計算不可: Calendar を使えば計算できます。
- 関連例:
```swift
import Foundation

var calendar = Calendar(identifier: .gregorian)
calendar.timeZone = TimeZone(secondsFromGMT: 0) ?? calendar.timeZone
let base = Date(timeIntervalSince1970: 0)
if let next = calendar.date(byAdding: .day, value: 1, to: base) {
    print(Int(next.timeIntervalSince1970))
}
```
- 関連例の出力: 86400
- 関連例の説明: UTC では 1 日がちょうど 86400 秒なのでこの値になりますが、夏時間のある地域では同じ計算でも秒数が変わります。だから暦の計算は Calendar に任せます。
- 覚えておくこと: 日付の加算は Calendar に任せる。86400 秒固定は危険。

## 06. Locale・FormatStyle・Measurement [Basic]

概要: 内部の値とユーザー向け表示を分離する。
考え方: 同じ数値や日付でも地域で表記が違う。

重要ポイント:
- Date.formattedで日付表示。
- 数値FormatStyleでcurrency/percent等。
- Localeで地域rule。
- Measurementで単位付き値。

コード:
```swift
let price=1234.5
let text=price.formatted(.currency(code:"JPY"))
```

なぜ重要か: 国際化、通貨、単位、日付表示で必要。
注意: 保存値と表示文字列を同一視しない。

確認問題:
Q1. FormatStyleの主用途は？ [Basic]
```swift
price.formatted(.currency(code:"JPY"))
```
A. ユーザー向け整形
B. DB作成
C. Actor化
D. Git管理
正解: A
解説: 値を用途/地域に応じて表示形式へ変換。

詳しい解説:
- 用語・考え方: FormatStyle は値を「人に見せるための文字列」へ変換する仕組みです。通貨記号の位置、桁区切り、小数点の記号などは国や言語で異なるため、Locale の情報に基づいて整形します。
- 正解になる理由: `price.formatted(.currency(code: "JPY"))` は金額を通貨表示に整えます。自前で文字列を組み立てるより、地域ごとの慣習に正しく従えます。
- 他の選択肢 DB作成: データの保存先を作る機能ではありません。表示のための変換です。
- 他の選択肢 Actor化: 並行処理での状態保護とは無関係です。
- 他の選択肢 Git管理: バージョン管理とは無関係です。
- 覚えておくこと: FormatStyle は表示用の整形。地域差を吸収する。

Q2. 内部Dateの扱いとして良いのは？ [Basic]
```swift
Date -> formatted String
```
A. 内部はDate、表示時format
B. 常にStringだけ
C. TimeZone無視
D. Locale固定
正解: A
解説: dataとpresentationを分離する。

詳しい解説:
- 用語・考え方: 同じ時刻でも、表示は地域・言語・画面によって変わります。そこで内部では Date のまま保持し、画面に出す直前だけ文字列へ整形するのが基本方針です。データと表示（presentation）を分ける考え方です。
- 正解になる理由: Date のまま持っていれば、比較・並べ替え・差分計算がそのまま行えます。文字列にしてしまうと、それらの操作のたびに解析し直す必要が生じます。
- 他の選択肢 常にStringだけ: 文字列だけで保持すると、比較や計算のたびに解析が必要になり、地域を変えた表示にも対応できません。
- 他の選択肢 TimeZone無視: TimeZone を無視すると、日付の境界がずれて別の日として扱われる不具合が起きます。
- 他の選択肢 Locale固定: 特定の Locale に固定すると、他の言語環境の利用者に合わない表示になります。
- 覚えておくこと: 内部は Date、表示の直前だけ文字列へ。

## 07. URL・URLComponents・Percent Encoding [Basic]

概要: URLを文字列連結ではなく構造として安全に組み立てる。
考え方: URLはscheme/host/path/queryなどの部品を持つ。

重要ポイント:
- URLでresource場所を表す。
- URLComponentsでqueryを構築。
- URLQueryItemを使う。
- Percent encodingを手書きしない。

コード:
```swift
var c=URLComponents(string:"https://example.com/search")!
c.queryItems=[URLQueryItem(name:"q",value:"Swift UI")]
```

なぜ重要か: 検索API、deep link、file URLで必須。
注意: String連結は空白や&などで壊れやすい。

確認問題:
Q1. Query parameterを安全に作る型は？ [Basic]
```swift
var c=URLComponents(...)
```
A. URLComponents
B. Calendar
C. Set
D. Dataだけ
正解: A
解説: URLComponentsとURLQueryItemを使う。

詳しい解説:
- 用語・考え方: URL には使える文字が決められており、空白や日本語、`&` `=` などの記号はそのままでは使えません。安全に扱うには percent encoding（%20 のような置き換え）が必要です。URLComponents は URL を「scheme・host・path・query」といった部品に分けて扱い、この変換を自動で行います。
- 正解になる理由: URLQueryItem で名前と値を渡せば、必要な文字だけが適切に変換されます。文字列連結では書き手が変換漏れを起こしがちです。
- 他の選択肢 Calendar: 暦の計算を扱う型で、URL とは無関係です。
- 他の選択肢 Set: 重複のない集合を表す型です。URL の組み立てには使いません。
- 他の選択肢 Dataだけ: Data は byte 列で、URL の構造は扱いません。
- 関連例:
```swift
import Foundation

var components = URLComponents(string: "https://example.com/search")
components?.queryItems = [URLQueryItem(name: "q", value: "leg day")]
if let url = components?.url {
    print(url.absoluteString)
}
```
- 関連例の出力: https://example.com/search?q=leg%20day
- 関連例の説明: 値に含まれる空白が %20 へ自動変換されています。文字列連結ではこの変換を自分で行う必要があり、漏れると壊れた URL になります。
- 覚えておくこと: query の組み立ては URLComponents + URLQueryItem。

Q2. URLをString連結しない主理由は？ [Basic]
```swift
"https://x.com?q="+query
```
A. 特殊文字encodingで壊れやすい
B. +禁止
C. URLはInt
D. 理由なし
正解: A
解説: 構造化APIでencodingを扱う方が安全。

詳しい解説:
- 用語・考え方: 検索語などの値には、空白・記号・日本語が入り得ます。これらを変換せずに URL へ連結すると、区切り記号として解釈されたり、そもそも URL として無効になったりします。値が外部由来の場合、意図しない書き換えを招く危険もあります。
- 正解になる理由: 文字列連結は「値の中身が安全である」という前提に依存します。URLComponents を使えばその前提が不要になり、変換漏れによる不具合を構造的に防げます。
- 他の選択肢 +禁止: `+` による文字列連結自体は文法として正しく、禁止されているわけではありません。問題は変換の欠落です。
- 他の選択肢 URLはInt: URL は数値ではありません。
- 他の選択肢 理由なし: 変換漏れという明確な理由があります。
- 覚えておくこと: URL を文字列連結で作らない。変換漏れが壊れる原因になる。

## 08. URLRequest・HTTP Method・Header・Status Code [Basic]

概要: HTTP通信を構成する基本要素を理解する。
考え方: 通信はURLだけでなくmethod/header/body/statusの契約。

重要ポイント:
- GET/POST/PUT/PATCH/DELETE。
- HeaderでContent-Type/Authorization等。
- BodyにJSON Data等。
- HTTP status codeを確認。

コード:
```swift
var request=URLRequest(url:url)
request.httpMethod="POST"
request.setValue("application/json",forHTTPHeaderField:"Content-Type")
```

なぜ重要か: API連携の最低限。HTTPの意味が分からないとdebugできない。
注意: transport成功でも404/500などapplication上の失敗はある。

確認問題:
Q1. Content-Typeが示すものは？ [Basic]
```swift
Content-Type: application/json
```
A. request bodyの形式
B. 通信速度
C. OS
D. Git branch
正解: A
解説: bodyのmedia typeを示す。

詳しい解説:
- 用語・考え方: HTTP ヘッダは、本体（body）に添える補足情報です。Content-Type はその中でも「body をどの形式として解釈すべきか」を示すもので、`application/json` なら受け取った側は JSON として解析します。
- 正解になる理由: 同じ byte 列でも、形式の宣言が違えばサーバー側の解釈が変わります。JSON を送っているのに Content-Type を付け忘れると、正しく解析されず失敗する原因になります。
- 他の選択肢 通信速度: 通信の速さを伝えるヘッダではありません。
- 他の選択肢 OS: クライアントの環境を伝えるのは User-Agent などの別のヘッダです。
- 他の選択肢 Git branch: バージョン管理とは無関係です。
- 覚えておくこと: Content-Type は body の形式の宣言。

Q2. URLSessionがthrowしなければstatusは必ず200？ [Basic]
```swift
let (data,response)=try await URLSession.shared.data(for:request)
```
A. 必ず200
B. HTTP statusを別途確認
C. 必ず404
D. response無し
正解: B
解説: network成功とHTTP成功は別。

詳しい解説:
- 用語・考え方: URLSession が例外を投げるのは、接続できない・タイムアウトしたなど「通信そのものが成立しなかった」場合です。サーバーに届いて 404 や 500 が返ってきた場合、通信としては成功しているため例外は投げられません。この 2 つは別の層の話です。
- コードの流れ: リクエストを送り、レスポンスを受け取る。
- コードの流れ: ここで例外が出なければ「サーバーまで届いて返事が来た」ことだけが分かる。
- コードの流れ: 返事の中身が成功か失敗かは、HTTPURLResponse の statusCode を見て判断する。
- コードの流れ: 2xx 以外ならアプリ側でエラーとして扱う。
- 正解になる理由: ネットワークの成功と、HTTP としての成功は別々に確認する必要があります。statusCode の確認を省くと、エラーページの本文を正常なデータとして解析しようとして失敗します。
- 他の選択肢 必ず200: 404 や 500 でも通信自体は成功しているため、例外は投げられません。200 とは限りません。
- 他の選択肢 必ず404: 特定の値に決まることはありません。サーバーの応答次第です。
- 他の選択肢 response無し: レスポンスは data と一緒に必ず返ります。
- 覚えておくこと: 例外が出ない ≠ HTTP 成功。statusCode を必ず確認する。

## 09. URLSession・async/await Networking [Intermediate]

概要: URLSessionで非同期通信を行い、response検証とdecodeまでつなげる。
考え方: 通信処理は request → await → status確認 → decode の流れで読む。

重要ポイント:
- data(for:)でDataとURLResponse。
- HTTPURLResponseへcastしてstatus確認。
- JSONDecoderでDTOへdecode。
- timeout/retry/cancellationは別途設計。

コード:
```swift
let (data,response)=try await URLSession.shared.data(for:request)
guard let http=response as? HTTPURLResponse,
      200..<300 ~= http.statusCode else { throw APIError.invalidResponse }
let dto=try JSONDecoder().decode(UserDTO.self,from:data)
```

なぜ重要か: ほぼすべてのnetwork appで必要。
注意: View内にrequest生成からdecodeまで全部書くとtestしづらい。

確認問題:
Q1. 200..<300 ~= statusCode の意味は？ [Intermediate]
```swift
guard 200..<300 ~= http.statusCode else { ... }
```
A. 2xx範囲か確認
B. 300以上だけ
C. String化
D. URL作成
正解: A
解説: statusが200以上300未満かpattern matchingしている。

詳しい解説:
- 用語・考え方: `~=` はパターンマッチ演算子で、左辺のパターンに右辺の値が含まれるかを判定します。`200..<300` は 200 以上 300 未満の範囲なので、`200..<300 ~= statusCode` は「statusCode が 2xx か」の判定になります。switch の case で範囲を書いたときも内部でこの演算子が使われています。
- 正解になる理由: HTTP の成功を表すのは 200 番台全体です。200 だけを見ると、204（成功だが本文なし）や 201（作成成功）を誤ってエラー扱いしてしまいます。
- 他の選択肢 300以上だけ: `..<` は上限を含まないため、300 以上は範囲外です。判定しているのは 2xx です。
- 他の選択肢 String化: 文字列への変換とは無関係です。
- 他の選択肢 URL作成: URL の生成とは無関係です。
- 関連例:
```swift
let range = 200..<300
print(range ~= 204)
print(range ~= 404)
print(range ~= 300)
```
- 関連例の出力: true
false
false
- 関連例の説明: 204 は 2xx なので成功、404 は範囲外、300 は上限に含まれないため false です。`..<` が上限を含まない点がここで効いています。
- 覚えておくこと: 成功判定は 200 だけでなく 200..<300 で行う。

Q2. JSON Dataを型へ変換するのは？ [Intermediate]
```swift
let (data,_)=try await URLSession.shared.data(from:url)
```
A. JSONDecoder
B. Calendar
C. FileManager
D. Set
正解: A
解説: Decodable型へdecodeする。

詳しい解説:
- 用語・考え方: URLSession が返すのは Data、つまり byte 列です。アプリの中で扱うには、その byte 列を Swift の型に対応付ける必要があり、JSON 形式ならその役割を担うのが JSONDecoder です。データの向きは ネットワーク → Data → Swift の型 です。
- 正解になる理由: 受け取った Data を decode に渡すことで、キーがプロパティへ対応付けられた型の値になります。以降は型として安全に扱えます。
- 他の選択肢 Calendar: 暦の計算を行う型で、データ変換は行いません。
- 他の選択肢 FileManager: ファイルの読み書きや管理を行う型です。JSON の解析はしません。
- 他の選択肢 Set: 重複のない集合を表す型で、変換の機能はありません。
- 覚えておくこと: 受信した Data は JSONDecoder で型へ変換する。

## 12. NotificationCenter [Intermediate]

概要: 1対多のevent通知を疎結合に配信する仕組みを理解する。
考え方: 送信者が受信者を直接知らずに『出来事』をbroadcastする。

重要ポイント:
- Notification.Nameでevent種別。
- 複数observerが受信可能。
- object/userInfoでpayload。
- 型安全性はdelegate/closureより弱くなりやすい。

コード:
```swift
NotificationCenter.default.post(name:.didLogout,object:nil)
```

なぜ重要か: app全体eventやlegacy codeで遭遇する。
注意: 何でもNotificationCenterにすると依存関係が見えなくなる。

確認問題:
Q1. NotificationCenterが向く性質は？ [Intermediate]
```swift
NotificationCenter.default.post(...)
```
A. 1対多event通知
B. 型継承
C. JSON decode
D. Auto Layout
正解: A
解説: broadcast用途。

詳しい解説:
- 用語・考え方: NotificationCenter は「送り手が受け手を知らないまま、出来事を broadcast する」仕組みです。1 つの通知に対して受け手が 0 人でも複数人でも成り立ち、送り手側のコードは変わりません。
- 正解になる理由: キーボードの表示やアプリの状態変化など、誰が関心を持つか送り手には分からない出来事の通知に向いています。
- 他の選択肢 型継承: 型の継承関係とは無関係な、実行時の通知の仕組みです。
- 他の選択肢 JSON decode: JSON の解析は Codable と JSONDecoder の役割です。
- 他の選択肢 Auto Layout: 画面のレイアウトとは関係ありません。

Q2. 乱用時の問題は？ [Intermediate]
```swift
post(name:...,object:nil)
```
A. 依存関係やdata型が追いづらい
B. 必ずcompile error
C. 通信不能
D. ARC停止

詳しい解説:

- 他の選択肢 通信不能: 通信の可否とは無関係です。
- 他の選択肢 ARC停止: メモリ管理が止まることはありません。ただし解除し忘れると不要な購読が残ることはあります。
- 覚えておくこと: 便利だが依存関係が見えなくなる。関係が固定なら明示的な手段を。

## 13. Regex・RegexBuilder [Intermediate]

概要: 文字列patternを検索・検証する。

- Regex literalを利用可能。
- wholeMatch/firstMatch等で判定。
- capture部分を取り出せる。
- 複雑なRegexは分解してtest。

コード:
```swift
let regex=/\d{4}-\d{2}-\d{2}/
let matched="2026-07-24".wholeMatch(of:regex) != nil
```

なぜ重要か: 入力検証、log解析、text抽出で便利。
注意: 仕様全体を巨大な1本のRegexで完全検証しようとしない。

確認問題:
Q1. wholeMatchの特徴は？ [Intermediate]
```swift
"2026-07-24".wholeMatch(of:/\d{4}-\d{2}-\d{2}/)
```
A. 文字列全体が一致するか
B. 先頭1文字だけ
C. HTTP通信
D. Dateへ自動変換
正解: A
解説: 入力全体とのmatchを確認する。

詳しい解説:
- 用語・考え方: 正規表現の照合には範囲の違いがあります。wholeMatch は「入力全体がパターンに一致するか」、firstMatch は「どこかに一致する部分があるか」を調べます。入力の検証には、余計な文字が混ざっていないことを確認できる wholeMatch が向いています。
- 正解になる理由: `\d{4}-\d{2}-\d{2}` に対して wholeMatch を使えば、日付だけで構成された文字列かどうかを判定できます。前後に別の文字があれば一致しません。
- 他の選択肢 先頭1文字だけ: 先頭 1 文字だけを見る API ではありません。全体を対象とします。
- 他の選択肢 HTTP通信: 通信とは無関係です。
- 他の選択肢 Dateへ自動変換: 一致の判定を行うだけで、日付の型へ変換はしません。変換は別途行います。
- 関連例:
```swift
import Foundation

do {
    let pattern = try Regex(#"\d{4}-\d{2}-\d{2}"#)
    print("2026-07-24".wholeMatch(of: pattern) != nil)
    print("x2026-07-24".wholeMatch(of: pattern) != nil)
    print("x2026-07-24".firstMatch(of: pattern) != nil)
} catch {
    print("invalid pattern")
}
```
- 関連例の出力: true
false
true
- 関連例の説明: 余計な文字が付くと wholeMatch は一致しませんが、firstMatch は部分一致するため true になります。ここでは文字列からパターンを作っていますが、新しい言語モードでは設問のような /.../ というリテラル記法も使えます。
- 覚えておくこと: 検証は wholeMatch、抽出は firstMatch。

Q2. 複雑なRegexで重要なのは？ [Intermediate]
```swift
/.../
```
A. 具体例/反例をtest
B. 1行へ詰める
C. force unwrap
D. UI限定
正解: A
解説: 境界条件をtestする。

詳しい解説:
- 用語・考え方: 正規表現は短く書けても、境界の挙動が直感と食い違いやすい記法です。「一致してほしい例」だけでなく「一致してほしくない例（反例）」も含めて確認しないと、通しすぎ・弾きすぎに気づけません。
- 正解になる理由: 具体例と反例を並べて検証することで、意図した範囲だけを受け付けているかを確認できます。テストとして残せば、後から式を変えたときの崩れにも気づけます。
- 他の選択肢 1行へ詰める: 1 行に詰めても読みやすくはなりません。複雑なものは RegexBuilder で分解するほうが保守しやすくなります。
- 他の選択肢 force unwrap: Optional を無理に外す書き方は、一致しなかった場合に停止する原因になります。
- 他の選択肢 UI限定: 正規表現は入力検証やログ解析など、画面以外でも広く使われます。
- 覚えておくこと: 正規表現は「通る例」と「通らない例」の両方で確認する。

## 14. Sequence・Collection・Lazy [Intermediate]

概要: Arrayの下にある抽象化と遅延評価を理解する。
考え方: Sequenceは順番に値を取り出せ、Collectionはindex等のより強い保証を持つ。

重要ポイント:
- Sequenceはfor-in可能。
- Collectionはindex等を追加保証。
- lazyで変換を必要時まで遅延。
- 巨大dataで中間配列を減らせる場合。

コード:
```swift
let result=(1...1_000_000).lazy.map{$0*2}.first{$0>100}
```

なぜ重要か: 標準library APIとperformance理解につながる。
注意: lazyを付ければ常に高速ではない。

確認問題:
Q1. lazyの主特徴は？ [Intermediate]
```swift
(1...100).lazy.map{$0*2}
```
A. 必要まで変換を遅延
B. 必ず並列化
C. DB保存
D. Optional化
正解: A
解説: 要素要求まで評価を遅らせる。

詳しい解説:
- 用語・考え方: 通常の map は、その場ですべての要素を変換した新しい配列を作ります。lazy を挟むと変換は即座に行われず、実際に要素が必要になった時点で 1 つずつ計算されます。先頭数件しか使わない場合や、途中で打ち切る場合に無駄な計算を避けられます。
- 正解になる理由: 評価が必要になるまで遅らせるのが lazy の本質です。並列に実行されるわけではなく、あくまで「いつ計算するか」を変える最適化です。
- 他の選択肢 必ず並列化: 実行を並列化する機能ではありません。処理の順番は変わらず、タイミングだけが遅れます。
- 他の選択肢 DB保存: 保存とは無関係です。
- 他の選択肢 Optional化: 値の有無を表す Optional とは関係ありません。
- 関連例:
```swift
var evaluated = 0
let doubled = (1...100).lazy.map { (value: Int) -> Int in
    evaluated += 1
    return value * 2
}
print(doubled.first ?? 0)
print(evaluated)
```
- 関連例の出力: 2
1
- 関連例の説明: 100 要素あっても、先頭 1 件しか使わなければ変換は 1 回しか実行されません。lazy を外すと 100 回実行されます。
- 覚えておくこと: lazy は「必要になるまで計算しない」。並列化ではない。

Q2. CollectionがSequenceより追加する代表能力は？ [Intermediate]
```swift
Collection
```
A. index access等
B. 必ずSet
C. 必ず参照型
D. HTTP通信
正解: A
解説: より強い走査/indexの保証を持つ。

詳しい解説:
- 用語・考え方: Sequence は「先頭から順に 1 回ずつ取り出せる」ことだけを保証します。Collection はそれに加えて、何度でも走査できること、位置を表す index があること、count を有限時間で得られることなどを保証します。
- 正解になる理由: index による位置指定のアクセスは Collection 以降で使える能力です。Sequence だけでは一度きりの走査しか保証されないため、添字アクセスができません。
- 他の選択肢 必ずSet: Set は Collection の 1 つですが、Collection が Set になるわけではありません。Array も Collection です。
- 他の選択肢 必ず参照型: Array は struct であり値型です。参照型である必要はありません。
- 他の選択肢 HTTP通信: 通信の機能とは無関係です。
- 覚えておくこと: Collection は Sequence に index と再走査を足したもの。

## 15. DTO・Domain Model・Value Object・ID [Intermediate]

概要: データを外部形式・アプリの意味・表示へ分けて設計する。
考え方: data型は単なる入れ物ではなく、不正状態を作らせない設計手段。

重要ポイント:
- DTOはAPI/保存形式の境界。
- Domain Modelはapp内の意味。
- Value Objectで単位/制約を型に閉じ込める。
- 安定IDと表示indexを区別。

コード:
```swift
struct UserDTO:Decodable{let user_id:Int}
struct User:Identifiable{let id:Int}
func map(_ dto:UserDTO)->User{User(id:dto.user_id)}
```

なぜ重要か: 中規模以上で変更影響を小さくしtestしやすくする。
注意: 何でも巨大な1 Modelへまとめない。

確認問題:
Q1. DTOを分ける主目的は？ [Intermediate]
```swift
API JSON -> UserDTO -> User
```
A. 外部形式変更を内部から分離
B. 必ずcode量削減
C. UI自動生成
D. ARC無効
正解: A
解説: 外部仕様との境界を作れる。

詳しい解説:
- 用語・考え方: API のレスポンス形式は、こちらの都合とは無関係に変わることがあります。DTO を挟むと、その変化を受け止める層が 1 か所に定まり、アプリ内部のモデルはそのままで済みます。
- 正解になる理由: 変換処理という明確な境界を置くことで、外部仕様の変更が内部へ波及しにくくなります。テストのときも、DTO の解析と内部ロジックを別々に検証できます。
- 他の選択肢 必ずcode量削減: 型が増えるため、コード量はむしろ増えることが多いです。得られるのは変更に強い構造です。
- 他の選択肢 UI自動生成: UI が自動生成されることはありません。
- 他の選択肢 ARC無効: メモリ管理とは無関係です。
- 覚えておくこと: DTO は外部変更の受け止め役。内部モデルを守る。

Q2. indexとIDの違いは？ [Intermediate]
```swift
items[index].id
```
A. indexは位置、IDは同一性
B. 常に同じ
C. IDは表示位置
D. indexはUUID
正解: A
解説: 並べ替えでindexは変わる。

詳しい解説:
- 用語・考え方: index は「今この並びの中で何番目にあるか」という位置の情報で、並べ替えや削除で簡単に変わります。ID は「それがどの要素なのか」を表す同一性の情報で、並び順が変わっても要素に付いて回ります。
- 正解になる理由: 位置と同一性は別の概念です。選択中の要素を index で覚えていると、並べ替えた瞬間に別の要素を指してしまいます。ID で覚えていれば正しく追随します。
- 他の選択肢 常に同じ: 並べ替えを行えば一致しなくなります。常に同じではありません。
- 他の選択肢 IDは表示位置: ID は表示上の位置を表しません。位置を表すのは index です。
- 他の選択肢 indexはUUID: index は整数の位置であり、UUID のような識別子ではありません。
- 関連例:
```swift
struct Exercise: Identifiable { let id: Int; let name: String }
var exercises = [Exercise(id: 10, name: "squat"), Exercise(id: 20, name: "bench")]
print(exercises[0].id)
exercises.reverse()
print(exercises[0].id)
```
- 関連例の出力: 10
20
- 関連例の説明: 同じ index 0 でも、並べ替えの前後で別の要素を指しています。要素を特定したいときは index ではなく id を使います。
- 覚えておくこと: index は位置、ID は同一性。並べ替えで差が出る。

## 16. Copy-on-Write・Value Semantics [Intermediate]

概要: Array/String/Dictionary等が値型として振る舞いつつ効率よくcopyされる考え方を知る。
考え方: 見た目はcopyでも内部共有し、変更時に実copyする最適化がある。

重要ポイント:
- 標準Collectionは値semantics。
- 片方変更が他方へ影響しない。
- Copy-on-Writeで不要copyを避ける。
- 値semanticsと内部memory共有は別。

コード:
```swift
var a=[1,2,3]
var b=a
b.append(4)
print(a)
```

なぜ重要か: struct/Arrayのperformanceと意味を正しく理解する。
注意: 値型=毎回即フルcopyと単純化しない。

確認問題:
Q1. b.append後のaは？ [Intermediate]
```swift
var a=[1,2]
var b=a
b.append(3)
```
A. [1,2]
B. [1,2,3]
C. nil
D. 未定義
正解: A
解説: Arrayは値semantics。

詳しい解説:
- 用語・考え方: Array は struct であり値型です。代入すると論理的には中身がコピーされ、以降は互いに独立します。片方に要素を追加しても、もう片方の要素数は変わりません。
- コードの流れ: a は [1, 2]。
- コードの流れ: `var b = a` で b は a と独立した値になる。
- コードの流れ: b.append(3) は b 側だけを変更する。
- コードの流れ: a は [1, 2] のまま。
- 正解になる理由: 値型のコピーは独立しているため、意図しない共有による書き換えが起きません。
- 他の選択肢 [1,2,3]: b 側の結果です。参照型であればこうなりますが、Array は値型です。
- 他の選択肢 nil: 配列が nil になることはありません。
- 他の選択肢 未定義: 動作は仕様として明確に定まっています。
- 関連例:
```swift
var a = [1, 2]
var b = a
b.append(3)
print(a)
print(b)
```
- 関連例の出力: [1, 2]
[1, 2, 3]
- 関連例の説明: 代入した時点では中身を共有していますが、b を変更した瞬間に実際のコピーが作られ、a は影響を受けません。
- 覚えておくこと: Array の代入は独立したコピーとして振る舞う。

Q2. Copy-on-Writeとは？ [Intermediate]
```swift
var b=a
```
A. 変更時まで実copyを遅らせる最適化
B. 必ず参照型化
C. 非同期化
D. JSON化
正解: A
解説: 値semanticsを保ちつつcopy costを抑える。

詳しい解説:
- 用語・考え方: Copy-on-Write（COW）は、代入のたびに実際のコピーを作るのではなく、内部の記憶領域を共有しておき、どちらかが変更された瞬間に初めて本物のコピーを作る最適化です。利用者から見た振る舞いは値型のコピーそのままで、コストだけが下がります。
- コードの流れ: `var b = a` の時点では、a と b が同じ記憶領域を共有している（コピーはまだ発生しない）。
- コードの流れ: b に変更が加わる直前に、共有されているかどうかが確認される。
- コードの流れ: 共有されていれば、その時点で b 用の複製が作られる。
- コードの流れ: 以降 b への変更は a に影響しない。
- 正解になる理由: 大きな配列を代入しただけで毎回全要素を複製していては非効率です。COW により、読み取るだけなら複製せず、変更するときだけ複製します。
- 他の選択肢 必ず参照型化: 参照型に変わるわけではありません。値型の振る舞いを保ったままコストを下げる仕組みです。
- 他の選択肢 非同期化: 非同期処理とは無関係です。
- 他の選択肢 JSON化: データ変換とは無関係です。
- 覚えておくこと: COW は「変更するまでコピーしない」。値型の意味は変わらない。
