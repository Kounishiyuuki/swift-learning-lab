# SwiftUI

Swiftとは別レイヤーとして、View、状態、データフロー、Navigationを学ぶ。

このファイルは人が読みやすい教材原本です。構造化データは content.json、完成版は index.html です.

## 01. View・宣言的UI [Beginner]

概要: SwiftUIでは「どう変更するか」ではなく「今どう見えるべきか」を記述する。
考え方: View は画面そのものではなく、現在の状態からUIを説明する値。

重要ポイント:
- View は protocol。
- body は現在のUI構造を返す。
- 状態が変わると SwiftUI が必要な差分を反映する。
- View は小さな部品に分割して合成する。

コード:
```swift
struct CounterView: View {
    var count: Int

    var body: some View {
        Text("Count: \(count)")
    }
}
```

なぜ重要か: UIKit の命令的更新との最大の違い。SwiftUIを理解する中心概念。
注意: body を『一度だけ作られる画面』と考えない。状態に応じて評価されるUI記述。

確認問題:
Q1. SwiftUIの宣言的UIの説明として最も近いものは？ [Beginner]
```swift
Text("Hello")
```
A. ピクセルを直接描く
B. 現在どう見えるべきかを記述する
C. UIViewを必ず継承する
D. SQLでUIを作る
正解: B
解説: SwiftUIは状態から『UIがどうあるべきか』を宣言し、実際の更新はフレームワーク側が処理する。

詳しい解説:
- 用語・考え方: 宣言的 UI とは、「今の状態のとき画面はこう見えるべきだ」を書く方式です。命令的 UI（UIKit など）では「ラベルの文字を書き換える」「行を挿入する」といった手順を自分で書きますが、SwiftUI では状態と見た目の対応だけを書き、状態が変わったときの差分更新はフレームワークが担当します。
- コードの流れ: 状態（@State などの値）が変化する。
- コードの流れ: SwiftUI がその View の body を再度評価し、新しい「あるべき姿」を得る。
- コードの流れ: 前回の結果と比較し、実際に変わった部分だけを画面へ反映する。
- 正解になる理由: body は「現在の状態に対応する画面の記述」であり、毎回どこをどう書き換えるかを指示するものではありません。状態と見た目の対応が 1 か所に集まるため、更新漏れによる表示の食い違いが起きにくくなります。
- 他の選択肢 ピクセルを直接描く: 描画そのものを自分で行う低レベルな方式です。SwiftUI はその層を隠します。
- 他の選択肢 UIViewを必ず継承する: UIKit のクラス階層に基づく方式で、SwiftUI の View は struct として定義する protocol です。
- 他の選択肢 SQLでUIを作る: データベースの問い合わせ言語であり、UI の記述とは無関係です。
- 覚えておくこと: 「どう変えるか」ではなく「今どう見えるべきか」を書く。

Q2. `some View` の役割として近いものは？ [Basic]
```swift
var body: some View { Text("Hi") }
```
A. Viewに準拠する具体型を隠して返す
B. 必ずAnyViewに変換する
C. UIKit専用
D. Optional Viewを表す
正解: A
解説: `some View` は opaque result type。View に準拠する具体的な型をコンパイラが把握しつつ、呼び出し側には抽象化して示す。

詳しい解説:
- 用語・考え方: `some View` は opaque result type（不透明な戻り値の型）です。VStack や Text を組み合わせると型は入れ子になって非常に長くなりますが、`some View` と書けば「View に準拠した何か 1 つの具体型」とだけ示せます。コンパイラは具体型を把握しているため、型チェックや最適化は通常どおり働きます。
- 正解になる理由: 書き手は複雑な型名を書かずに済み、呼び出し側は中身の型に依存しなくなります。それでいて具体型は 1 つに定まっています。
- 他の選択肢 必ずAnyViewに変換する: AnyView は型を実行時に包んで消す仕組みで、差分更新の効率が落ちることがあります。some View は型を保ったまま隠すだけで、変換は行いません。
- 他の選択肢 UIKit専用: SwiftUI の機能であり、UIKit のための構文ではありません。
- 他の選択肢 Optional Viewを表す: 値の有無を表す Optional とは無関係です。
- 関連例:
```swift
import SwiftUI

struct TitleView: View {
    var body: some View {
        VStack {
            Text("Workout")
            Text("today")
        }
    }
}
```
- 関連例の説明: body の実際の型は VStack<TupleView<(Text, Text)>> のような入れ子ですが、some View と書くことでその複雑さを表に出さずに済みます。
- 覚えておくこと: some View は「型名は隠すが具体型は 1 つ」。AnyView とは違う。

## 02. Stack・Modifier・Layout [Basic]

概要: VStack / HStack / ZStack と Modifier の合成を理解する。
考え方: modifier は元Viewを直接書き換えるというより、修飾された新しいViewを返す連鎖として読む。

重要ポイント:
- VStack は縦、HStack は横、ZStack は重ねる。
- modifier の順序で結果が変わることがある。
- padding / frame / background の適用順を意識する。
- Spacer で余白を柔軟に配分する。

コード:
```swift
Text("Swift")
    .padding()
    .background(.blue)
    .clipShape(.capsule)
```

なぜ重要か: SwiftUIコードの大半はViewの合成。修飾順序を読めるとレイアウトの原因を追いやすい。
注意: `background().padding()` と `padding().background()` は見た目が異なる。

確認問題:
Q1. 縦方向にViewを並べるのは？ [Basic]
```swift
// A ? { Text("A"); Text("B") }
```
A. HStack
B. VStack
C. ZStack
D. ListRow
正解: B
解説: VStack は Vertical Stack。子Viewを縦方向に配置する。

詳しい解説:
- 用語・考え方: Stack は子 View を並べるコンテナです。VStack は Vertical（縦）方向、HStack は Horizontal（横）方向、ZStack は奥行き方向に重ねて配置します。
- 正解になる理由: 縦に並べたいので VStack です。名前の頭文字が方向を表しています。
- 他の選択肢 HStack: Horizontal Stack で、子 View を横方向に並べます。
- 他の選択肢 ZStack: 手前と奥に重ねて配置します。背景の上に文字を乗せるときなどに使います。
- 他の選択肢 ListRow: そのような標準のコンテナはありません。行を並べたい場合は List を使います。
- 覚えておくこと: V は縦、H は横、Z は重ね。

Q2. modifier の順序について正しいものは？ [Basic]
```swift
Text("Hi").padding().background(.blue)
```
A. 順序は常に無関係
B. 順序によって結果が変わることがある
C. modifier は1つだけ使える
D. background はUIKit専用
正解: B
解説: 各 modifier は新しい View を返すため、どの段階に padding や background を適用するかで見た目が変わる。

詳しい解説:
- 用語・考え方: modifier は「View を受け取って、新しい View を返す」仕組みです。`.padding().background(.blue)` は「余白を足した View に背景を敷く」という順で適用されるため、背景は余白を含む範囲に広がります。順序を逆にすると、背景を敷いた View の外側に余白が付きます。
- コードの流れ: Text("Hi") がある。
- コードの流れ: `.padding()` が、その周囲に余白を加えた新しい View を返す。
- コードの流れ: `.background(.blue)` が、その（余白込みの）View の背後に色を敷く。
- コードの流れ: 結果として、余白部分まで青くなる。
- 正解になる理由: 各段階で対象となる View が変わるため、適用順によって見た目が変わります。modifier は設定項目の羅列ではなく、包む順序を表しています。
- 他の選択肢 順序は常に無関係: 順序が影響しない modifier もありますが、padding と background のように影響するものが多くあります。
- 他の選択肢 modifier は1つだけ使える: modifier はいくつでも連ねられます。
- 他の選択肢 background はUIKit専用: background は SwiftUI の modifier です。
- 覚えておくこと: modifier は包む順序。padding → background で余白まで色が付く。

## 03. @State・@Binding [Basic]

概要: 画面内の状態と、親子View間で共有する状態の入口。
考え方: @State はViewが所有する状態、@Binding は他の場所が所有する状態への読み書き可能な窓。

重要ポイント:
- @State はローカルなUI状態の所有に使う。
- @Binding は状態を所有せず参照する。
- 状態変更により関連Viewが更新される。
- データの所有者を曖昧にしない。

コード:
```swift
struct ToggleRow: View {
    @Binding var isOn: Bool

    var body: some View {
        Toggle("Enabled", isOn: $isOn)
    }
}
```

なぜ重要か: SwiftUIのバグは状態の所有場所が曖昧なときに起きやすい。誰がsource of truthかを決める。
注意: @Binding は値のコピーではない。親などが所有する状態への接続。

確認問題:
Q1. @State が最も向いているのは？ [Basic]
```swift
struct Screen: View {
    // ? var isPresented = false
}
```
A. 画面内だけで所有する表示状態
B. グローバルDB接続
C. UIViewControllerの継承
D. 定数
正解: A
解説: @State はViewが所有するローカル状態に適する。例えばシート表示やトグル状態。

詳しい解説:
- 用語・考え方: Property Wrapper とは、プロパティに共通の振る舞いを付け足す仕組みで、`@` を頭に付けて書きます。@State はその 1 つで、「この View が所有する、変化したら画面を更新すべき値」を表します。View は struct（値型）で再生成されますが、@State の値は SwiftUI 側で保持されるため、再生成をまたいで残ります。
- 正解になる理由: シートの表示有無やトグルの状態のように、その画面の中だけで完結し、その画面が持ち主である状態に向いています。
- 他の選択肢 グローバルDB接続: アプリ全体で共有する資源を View が所有するのは適切ではありません。外部から渡すか、専用の仕組みで管理します。
- 他の選択肢 UIViewControllerの継承: UIKit のクラスであり、SwiftUI の状態管理とは別の話です。
- 他の選択肢 定数: 変化しない値に @State は不要です。単なる let で十分です。
- 覚えておくこと: @State は「その View が持ち主である、変化する値」。

Q2. $isOn が意味するものは？ [Basic]
```swift
@State private var isOn = false
Toggle("On", isOn: $isOn)
```
A. Boolの反転
B. Binding<Bool>
C. String化
D. Optional化
正解: B
解説: $ を付けることで @State が提供する Binding を取り出し、Toggle が読み書きできる。

詳しい解説:
- 用語・考え方: @State は 2 つの値を公開します。1 つは本来の値（wrappedValue）で `isOn` と書くと得られます。もう 1 つが projectedValue で、`$isOn` と書くと得られる Binding<Bool> です。Binding は「読み取りと書き込みの両方ができる通り道」で、値そのもののコピーではありません。
- 正解になる理由: Toggle は利用者の操作に応じて値を書き換える必要があります。値のコピーを渡しても元に反映されないため、書き込みもできる Binding を `$` で渡します。
- 他の選択肢 Boolの反転: `$` は値を反転しません。真偽を反転するのは `!` です。
- 他の選択肢 String化: 文字列への変換とは無関係です。
- 他の選択肢 Optional化: 値の有無を表す Optional とは無関係です。
- 覚えておくこと: `$` は Binding（読み書きの通り道）を取り出す記号。

## 04. Observation・モデルと状態 [Intermediate]

概要: 複数Viewで扱うモデルをUI更新と結び付ける。
考え方: 画面に必要な状態をモデルに集め、Viewはその状態から表示を導出する。

重要ポイント:
- Observation を使うとモデルの変更をSwiftUIが追跡できる。
- Viewにロジックを詰め込みすぎず、モデルやサービスへ分離する。
- 派生値は保存せず計算できる場合が多い。
- 依存関係の所有範囲を意識する。

コード:
```swift
@Observable
final class CounterModel {
    var count = 0
}
```

なぜ重要か: 中規模以上では状態管理が設計品質を大きく左右する。
注意: 何でもグローバル共有すると依存関係が見えなくなり、テストもしにくくなる。

確認問題:
Q1. 状態モデルを分離する主な利点は？ [Intermediate]
```swift
@Observable final class Model { var count = 0 }
```
A. 必ず通信が速くなる
B. 状態とUIの責務を分けやすい
C. Viewが不要になる
D. UIKitに変換される
正解: B
解説: 状態・ロジックとUI記述を分けることで責務が明確になり、テストや再利用がしやすくなる。

詳しい解説:
- 用語・考え方: 画面の記述と、状態やロジックを別の型に分けると、それぞれの責務がはっきりします。@Observable を付けたクラスは、プロパティの変化が観測され、参照している View が自動的に更新されます。
- 正解になる理由: 状態とロジックが View から独立するため、UI を起動せずにロジックだけをテストでき、同じ状態を複数の View から使い回せます。
- 他の選択肢 必ず通信が速くなる: 通信の速さは変わりません。構造の話です。
- 他の選択肢 Viewが不要になる: View は引き続き必要です。役割が分かれるだけです。
- 他の選択肢 UIKitに変換される: 別のフレームワークへ変換される仕組みではありません。
- 覚えておくこと: 状態・ロジックと画面記述を分けると、テストしやすくなる。

Q2. 派生値の扱いとして良い設計は？ [Intermediate]
```swift
var firstName = "Yuki"
var lastName = "K"
// fullName は？
```
A. 必ず別の保存状態にする
B. 必要なら計算プロパティで導出する
C. UserDefaultsだけに置く
D. 常にglobalにする
正解: B
解説: 元データから必ず計算できる値は重複保存すると不整合が起きやすい。計算プロパティなどで導出する方が安全。

詳しい解説:
- 用語・考え方: 他の値から必ず計算できる値を、別途保存してしまうと、元の値が変わったときに更新し忘れて食い違いが生じます。計算プロパティとして導出すれば、常に元の値と一致します。
- 正解になる理由: fullName は firstName と lastName から必ず求まります。保存せず計算にすれば、どちらかを変えても自動的に正しい結果になります。
- 他の選択肢 必ず別の保存状態にする: 保存すると二重管理になり、更新漏れによる不整合の原因になります。
- 他の選択肢 UserDefaultsだけに置く: 永続化の場所の話であり、導出の是非とは別です。しかも同じ二重管理の問題が残ります。
- 他の選択肢 常にglobalにする: どこからでも触れる値にすると、変更元が追えなくなります。
- 関連例:
```swift
struct User {
    var firstName = "Yuki"
    var lastName = "K"
    var fullName: String { firstName + " " + lastName }
}
var user = User()
print(user.fullName)
user.lastName = "Kounishi"
print(user.fullName)
```
- 関連例の出力: Yuki K
Yuki Kounishi
- 関連例の説明: fullName を保存していないため、lastName を変えるだけで結果が追随します。保存していたら、更新処理を書き忘れた瞬間に古い値が残ります。
- 覚えておくこと: 導出できる値は保存しない。計算プロパティにする。

## 05. List・ForEach・NavigationStack [Intermediate]

概要: データの一覧表示と画面遷移を組み立てる。
考え方: 一覧はデータのIdentity、Navigationは遷移先を表す値を意識する。

重要ポイント:
- ForEach は各要素の安定した識別子が重要。
- Identifiable で id を型に持たせられる。
- NavigationStack は値ベースのNavigationを構成できる。
- 画面遷移とデータ選択を分離して考える。

コード:
```swift
NavigationStack {
    List(items) { item in
        NavigationLink(value: item) {
            Text(item.name)
        }
    }
}
```

なぜ重要か: 実アプリの基本構造。IDが不安定だとアニメーションや更新差分で問題が出る。
注意: 配列indexを恒久的IDとして使うと、並べ替え・削除時にIdentityがずれることがある。

確認問題:
Q1. ForEachで安定したidが重要な理由は？ [Intermediate]
```swift
ForEach(items) { item in Text(item.name) }
```
A. 文字色を決めるため
B. 要素の同一性と差分更新を追跡するため
C. ネット通信のため
D. Optionalをなくすため
正解: B
解説: SwiftUIはidを使って前後の要素を対応付け、挿入・削除・更新を判断する。

詳しい解説:
- 用語・考え方: SwiftUI は再評価のたびに「前回の要素」と「今回の要素」を突き合わせ、どれが追加・削除・移動されたかを判断します。その対応付けに使うのが id です。id が安定していないと、同じ要素を別物と見なして作り直してしまい、状態やアニメーションが崩れます。
- 正解になる理由: id は要素の同一性を示す情報です。並び順が変わっても、同じ id の要素は同じものとして追跡されます。
- 他の選択肢 文字色を決めるため: 見た目の指定とは無関係です。
- 他の選択肢 ネット通信のため: 通信とは無関係です。
- 他の選択肢 Optionalをなくすため: 値の有無を表す Optional とは無関係です。
- 覚えておくこと: id は要素の同一性。差分更新の土台になる。

Q2. NavigationStackの役割は？ [Intermediate]
```swift
NavigationStack { ContentView() }
```
A. 画面遷移のスタックを管理する
B. Auto Layoutを有効化する
C. JSONを解析する
D. ARCを無効化する
正解: A
解説: NavigationStack は階層的な画面遷移とnavigation pathを管理するコンテナ。

詳しい解説:
- 用語・考え方: NavigationStack は、画面を積み重ねて進み、戻ると取り除かれるという遷移の履歴を管理するコンテナです。積まれている経路（path）を値として扱えるため、コードから特定の画面へ遷移したり、まとめて戻したりできます。
- 正解になる理由: 遷移の履歴をスタックとして持つのが役割です。個々の画面の中身とは独立しています。
- 他の選択肢 Auto Layoutを有効化する: 制約による配置は UIKit の仕組みで、SwiftUI では別のレイアウト方式を使います。
- 他の選択肢 JSONを解析する: データの解析とは無関係です。
- 他の選択肢 ARCを無効化する: メモリ管理は通常どおり働きます。
- 覚えておくこと: NavigationStack は遷移の履歴（積み重ね）を管理する。

## 06. .task・非同期処理・MainActor [Intermediate]

概要: Viewのライフサイクルに合わせて非同期処理を開始し、UI状態を安全に更新する。
考え方: 通信処理そのものと、通信結果を画面状態へ反映する処理を分けて読む。

重要ポイント:
- .task でViewに関連した非同期処理を開始できる。
- Taskはキャンセルされる可能性を考慮する。
- UIに関係する状態はMainActorとの関係を理解する。
- 通信ロジックをViewへ直接詰め込みすぎない。

コード:
```swift
.task {
    do {
        items = try await repository.fetchItems()
    } catch {
        errorMessage = error.localizedDescription
    }
}
```

なぜ重要か: 現代のアプリは非同期処理が前提。Swift ConcurrencyとSwiftUIを接続する重要部分。
注意: View表示のたびに重い処理を無条件で走らせると、重複リクエストなどが起きる可能性がある。

確認問題:
Q1. .task の用途として近いものは？ [Intermediate]
```swift
Text("Loading").task { await load() }
```
A. Viewに関連した非同期処理を開始する
B. Auto Layout制約を作る
C. Storyboardを開く
D. classをstructへ変換する
正解: A
解説: .task はViewのライフサイクルに関連付いた非同期処理を実行するために使える。

詳しい解説:

Q2. 非同期ロード設計で重要なのは？ [Intermediate]
```swift
let items = try await api.fetchItems()
```
A. 必ずsleepする
B. 失敗・キャンセル・状態更新を考慮する
C. 全処理を同期化する
D. Optionalを禁止する
正解: B
解説: ネットワーク処理は失敗やキャンセルがあり得る。loading / success / error などの状態を設計する。

詳しい解説:
- 用語・考え方: ネットワークからの読み込みは、成功だけでなく失敗もキャンセルも起こります。「読み込み中」「成功（データあり）」「失敗（理由あり）」といった状態を型で表し、それぞれに対応する画面を用意しておくと、表示の抜けが生じません。
- 正解になる理由: 失敗時に何も出ない、読み込み中と空データが区別できない、といった問題は状態設計の不足から起きます。enum で状態を表せば、switch で扱い漏れを防げます。
- 他の選択肢 必ずsleepする: 待ち時間を入れても問題は解決しません。
- 他の選択肢 全処理を同期化する: 同期化すると、その間 UI が固まります。
- 他の選択肢 Optionalを禁止する: 値が無い可能性は実際に存在するため、表現を禁止しても解決しません。
- 覚えておくこと: loading / success / failure を状態として設計する。
